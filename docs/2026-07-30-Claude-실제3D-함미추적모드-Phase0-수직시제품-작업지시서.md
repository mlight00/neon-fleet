## 0. 한 문장 목표

현재 2.5D 함미 추적 시점의 1980년대식 가짜 입체감을 보완하기 위해, 기존 2D 게임 규칙은 전혀 바꾸지 않고 대표 기함과 대표 적을 **실제 3D 형상·원근·조명으로 렌더링**하는 선택형 시제품을 만든다.

이 단계의 성공 기준은 “기능이 돌아간다”가 아니다.

> 최대 확대에서 사용자가 기함의 함미·측면·엔진·무장 구조를 실제 입체로 인식하고, 기존 RC2보다 기함을 가까이 보고 조종하는 즐거움이 분명히 커졌다고 느껴야 한다.

## 3. 핵심 제품 결정

### 3.1 게임의 진실은 계속 2D이다

기존 2D 게임 상태를 단일 진실 공급원으로 유지한다.

- 위치와 이동
- 충돌 판정
- 공격 판정
- 피격 판정
- 스폰
- 보상
- 진행도
- RNG와 seed
- 저장 데이터
- 밸런스

Three.js는 위 상태를 읽어 **같은 순간을 3D로 보여주는 렌더러**일 뿐이다. Three.js의 `Raycaster`, 물리 엔진, 3D 객체 위치를 전투 판정의 진실로 사용하지 않는다.

이 계약을 지키면 3D가 실패하거나 느린 기기에서도 현재 RC2로 안전하게 복귀할 수 있다.

### 3.2 기본 공개 버전은 계속 RC2이다

- 일반 URL: 현재 RC2 동작 유지
- `?chase3d=1`: Phase 0 실제 3D 사용 가능
- `?chase3d=1&chase3dTest=1`: 결정적 3D 검증 장면

기능 플래그가 없을 때는 Three.js 모듈을 내려받거나 초기화하지 않는다. WebGL 캔버스도 만들지 않는 것을 원칙으로 한다.

### 3.3 3D 실패 시 화면이 비면 안 된다

다음 상황에서는 예외 없이 현재 2.5D RC2를 유지하거나 즉시 복귀한다.

- Three.js 모듈 로딩 실패
- WebGL 미지원
- 컨텍스트 생성 실패
- `webglcontextlost`
- 모델 생성 또는 로딩 실패
- 미지원 개체가 핵심 장면에 등장
- 프레임 성능이 안전 하한을 지속적으로 밑돎

오류는 개발 모드에서만 명확히 기록하고, 일반 플레이어에게는 빈 화면이나 멈춤을 보이지 않는다.

### 4.2 실제 3D의 최소 품질

평면 스프라이트, 카메라를 항상 바라보는 빌보드, 2D 그림을 얇게 압출한 판만으로 완료 처리하지 않는다.

각 모델은 카메라에서 보이는 실제 앞·뒤·옆 표면과 깊이를 가져야 한다.

- 좌우 날개 또는 장갑 프레임
- 최소 2개의 엔진 노즐
- 무장 마운트
- 지휘 함교 또는 지휘 프레임
- 함미에서 보이는 추진광
- 움직일 때 약한 롤·뱅크 반응

#### B1 소형 크리처

- AURORA와 혼동되지 않는 날카로운 소형 실루엣
- 접근 방향을 인식할 수 있는 전·후면 차이
- 대량 등장해도 형태가 읽히는 단순한 구조

#### B4 Sniper

- 긴 사거리 또는 포신을 암시하는 실루엣
- 발사점이 명확한 무장 부위

#### B8 Reaper Lord

- 일반 적보다 명백히 큰 체급
- 보스 핵심부, 장갑, 주무장이 구분되는 구조
- 화면을 가려도 공격 판독을 방해하지 않는 실루엣

#### 시각 방향

- `FORGED LIGHT` 분위기 유지
- 어두운 도장 금속
- 지휘 계열의 금색 테두리
- 청록·마젠타 계열의 무장 발광
- 엔진 발광
- 현대적인 저폴리곤/PBR 인상
- 복셀, 철망선, 레트로 와이어프레임 스타일 금지

### 4.3 제작 방식

Phase 0은 외부 모델 구매나 전체 GLB 제작보다 **Three.js 기본 지오메트리를 조합한 모듈식 실제 3D 모델**을 우선한다.

- `BoxGeometry`, `CylinderGeometry`, `ConeGeometry`, `ExtrudeGeometry` 등을 조합할 수 있다.
- 좌우 날개, 엔진, 장갑판, 무장을 재사용 가능한 부품으로 만든다.
- 향후 H0~H5로 확장할 수 있도록 부품과 색상 설정을 분리한다.
- 작은 로컬 GLB가 실제로 필요할 때만 사용한다.
- 사용하지 않는 `GLTFLoader`나 대형 텍스처를 미리 포함하지 않는다.
- 외부 CDN, 외부 모델 URL, 실행 중 네트워크 의존은 금지한다.

권장 최대 복잡도:

- 기함: 15,000 triangles 이하
- 보스: 20,000 triangles 이하
- 일반 적: 개체당 3,000 triangles 이하
- 드론: 개체당 1,000 triangles 이하

폴리곤 수는 절대 목표가 아니라 성능 상한이다. 더 단순한 구조로 충분하면 더 적게 사용한다.

## 5. Three.js 도입 규칙

### 5.1 기술 선택

- 브라우저·게임 포털 호환성을 위해 `WebGLRenderer` 사용
- Three.js는 작업 시점의 안정 버전을 **정확한 버전으로 고정**
- 필요한 파일만 프로젝트 안에 로컬로 포함
- CDN import 금지
- Three.js MIT 라이선스와 버전·출처를 저장소 내 라이선스 문서에 기록
- Phase 0에서 GLB를 사용하지 않으면 `GLTFLoader`를 포함하지 않음

권장 렌더러 초기화:

```js
new WebGLRenderer({
  canvas,
  alpha: true,
  premultipliedAlpha: false,
  antialias: true,
  powerPreference: 'high-performance',
});
```

실제 환경에서 옵션 호환성을 확인하고, 실패하면 안전한 설정으로 한 번 재시도한 뒤 RC2로 복귀한다.

### 5.2 권장 모듈 경계

파일명은 현재 코드 구조에 맞게 조정해도 되지만 책임을 섞지 않는다.

```text
js/chase3d-config.js      기능 플래그, 품질 단계, 용량·성능 상수
js/chase3d-mapping.js     2D 월드 ↔ 3D 전장 좌표, 입력 역변환
js/chase3d-models.js      모듈식 모델 팩토리와 재질
js/chase3d-scene.js       scene/camera/light/object pool 수명주기
js/chase3d-renderer.js    RC2 상태를 읽어 장면 동기화·렌더링
tests/chase3d-*.test.mjs  좌표·수명주기·기능 플래그·결정성 검증
```

`main.js`와 `entities.js`에 Three.js 세부 구현을 대량으로 직접 넣지 않는다. 기존 2.5D 코드는 fallback이므로 제거하거나 난도 높은 재작성 대상으로 만들지 않는다.

## 6. 캔버스와 화면 계층

HUD가 3D 뒤로 숨지 않도록 화면 계층을 명시적으로 나눈다.

```text
DOM 버튼·일시정지·선택창
↑
canvas#game-hud   투명 2D HUD·경고·텍스트·화면 효과
↑
canvas#game3d     투명 WebGL 실제 3D 월드
↑
canvas#game       배경과 기존 2D/2.5D 월드
```

요구사항:

- `#game3d`, `#game-hud`는 `pointer-events: none`
- 실제 입력은 기존 `#game` 입력 계통이 계속 처리
- 세 캔버스는 같은 CSS 크기와 동일한 논리적 viewport를 사용
- resize, orientation change, devicePixelRatio 변화 시 함께 갱신
- HUD·일시정지·선택창·게이지·텍스트는 3D 카메라 영향을 받지 않음
- 기능 플래그가 없을 때 기존 화면은 RC2와 같아야 함
- 단순히 기존 draw 전체를 복사하여 HUD를 두 번 그리지 말고, 월드 단계와 HUD 단계를 명시적으로 분리

DOM 계층을 다른 방식으로 구현해도 되지만 위 결과와 fallback 안전성을 충족해야 한다.

## 7. 카메라 전환 계약

확대 배율은 기존 100~220%를 유지한다.

| 배율 | 표시 |
|---|---|
| 100~160% | 기존 2D/2.5D만 표시, WebGL 렌더 휴면 |
| 160~200% | 2D 월드와 3D 월드 교차 전환 |
| 200~220% | 실제 3D 함미 추적 표시 |

전환값:

```js
const raw = clamp((zoom - 1.6) / 0.4, 0, 1);
const t = raw * raw * (3 - 2 * raw); // smoothstep
```

- 2D 월드 alpha: `1 - t`
- 3D 월드 alpha: `t`
- 3D 카메라도 같은 `t` 계열의 easing으로 높은 각도에서 함미 추적 위치로 이동
- HUD alpha는 바꾸지 않음
- `prefers-reduced-motion: reduce`에서는 지연 애니메이션을 생략하되 상태는 정확히 전환
- 확대·축소를 빠르게 왕복해도 깜빡임, 중복 객체, 메모리 증가가 없어야 함

### 함미 추적 구도

- PerspectiveCamera
- 기함 뒤·위에서 진행 방향을 바라봄
- 기함이 화면 하단 약 30~40% 영역에 충분히 크게 보임
- 기함 전체 윤곽과 엔진이 잘리지 않음
- 멀리 있는 적과 게이트가 원근상 작아짐
- 플레이어 좌우 이동에는 카메라가 부드럽게 따라오며 기함은 약하게 뱅크
- 자유 회전이나 마우스 룩은 넣지 않음

## 8. 2D 상태를 3D로 옮기는 좌표 계약

개념 좌표는 다음을 기준으로 한다.

```js
X = (worldX - squadX) * scaleX;
Z = (squadY - worldY) * scaleZ; // 진행 방향
Y = visualAltitude;             // 시각 효과용 작은 높이
```

중요:

- 기존 `worldX`, `worldY`를 3D에 맞게 수정하지 않는다.
- 3D의 `Y`는 시각 표현일 뿐 충돌 판정에 사용하지 않는다.
- 같은 seed와 같은 입력이면 3D on/off의 실제 2D 게임 상태가 같아야 한다.
- 게이트의 3D 중앙선과 실제 2D 판정 중앙선이 일치해야 한다.
- 레이저와 투사체의 3D 발사점은 실제 공격 주체에 붙어 있어야 한다.

### 입력

함미 3D에서 마우스·터치 X 입력은 다음 중 하나로 정확히 역변환한다.

1. 카메라 광선을 플레이어 이동 평면과 교차
2. 동일한 투영 수식의 해석적 역변환

Three.js 객체를 직접 끌어 게임 좌표로 사용하는 방식은 금지한다.

검증 기준:

- 화면 X → 플레이어 평면 → 기존 논리 X 오차가 **2 logical px 이하**
- 좌·중앙·우 3지점과 6개 viewport에서 검증
- 빠른 카메라 전환 중에도 마지막 입력이 튀지 않음

## 9. 장면·성능 규칙

### 9.1 렌더링

- 기본 조명: `HemisphereLight` + `DirectionalLight`
- 금속/거칠기/발광을 절제해 사용
- Phase 0 실시간 그림자 금지
- Phase 0 포스트 프로세싱과 블룸 금지
- 엔진 발광은 저비용 emissive 재질 또는 작은 로컬 glow sprite 사용 가능
- 배경 우주는 기존 2D 자산을 재사용

### 9.2 반복 개체

- 드론과 동일 타입 반복 적은 `InstancedMesh` 사용
- 프레임마다 Mesh·Geometry·Material을 새로 만들지 않음
- 개체 pool을 사용하고 사라진 개체를 재사용
- 각 인스턴스 행렬과 색상 값은 유한값인지 검증
- 실제 개체 수와 instance count가 일치해야 함

### 9.3 픽셀 비율

- 데스크톱 WebGL pixel ratio 상한 권장: 1.5
- 모바일 WebGL pixel ratio 상한 권장: 1.0
- 성능 저하 시 내부 해상도만 낮추고 HUD는 선명하게 유지

### 9.4 수명주기

- 160% 미만에서는 WebGL 렌더 루프를 쉬게 함
- 장면 해제 시 geometry, material, texture를 명시적으로 `dispose()`
- resize 리스너와 context 리스너 중복 등록 금지
- 3D on/off 또는 100↔220% 왕복 20회 뒤 객체·리스너·GPU 자원 수가 계속 증가하지 않아야 함
- `webglcontextlost`를 처리하고 RC2 fallback을 표시

### 9.5 성능 목표

- 일반 데스크톱: 안정적인 60fps 목표
- 390×844 모바일: 최소 30fps 유지
- 같은 수의 개체를 표시한 RC2 대비 프레임 시간 악화 20% 이내를 목표로 측정
- 완료보고에는 평균 FPS만 쓰지 말고 최소한 평균 frame time, p95 frame time, draw calls, triangles, 활성 모델 수를 기록

성능 목표를 못 맞추면 숫자를 숨기지 말고 실패 원인과 가장 큰 병목을 적는다.

## 10. 용량 계약

현재 CrazyGames Basic 빌드는 약 44.70MB이므로 여유가 매우 작다.

Phase 0 목표:

- 새 3D 런타임·모델·재질·텍스처 총 추가량: **압축 전 3.0MB 이하**
- CrazyGames Basic 전체: **47.70MB 이하 목표**
- CrazyGames Basic 전체: **50MB 미만 절대 조건**
- 외부 네트워크 요청: **0건**

50MB를 맞추기 위해 기존 원본 에셋을 삭제하지 않는다.

만약 Three.js와 시제품만으로 목표를 넘으면 작업을 억지로 완료 처리하지 말고 다음을 별도 제안으로 보고한다.

1. 실제 포함된 Three.js 코드 크기
2. 3D 에셋별 크기
3. 현재 28.50MB인 음원 묶음의 안전한 포털 전용 최적화 가능성
4. 품질 저하 없이 줄일 수 있는 항목

## 12. 자동 테스트

기존 760개 테스트를 삭제·완화·skip하지 않는다.

최소 신규 검증:

### 12.1 기능 플래그

- 기본 URL에서는 Three.js import·초기화·WebGL canvas 생성 없음
- `chase3d=1`일 때만 동적 import와 초기화
- 초기화 실패 시 RC2 유지

### 12.2 결정성

같은 seed와 같은 입력으로 최소 600프레임 실행했을 때 3D off/on의 다음 2D 상태가 동일해야 한다.

- squad 위치와 체력
- 적 위치·체력·생존 여부
- 투사체
- gate 선택과 판정
- 점수·보상·진행도
- RNG 상태 또는 다음 RNG 결과

화면을 그리지 않은 대체 객체로 “같을 것”이라고 추정하지 말고 실제 A/B 경로를 통과시킨다.

### 12.3 좌표

- world→3D 변환의 방향과 크기
- 입력 역변환 오차 2 logical px 이하
- 6개 viewport의 좌·중·우
- 전환 중 유한값

### 12.4 객체 수명

- 반복 적·드론 instance count
- 프레임당 새 Geometry/Material 생성 없음
- 20회 모드 왕복 후 scene child, listener, pool, GPU 리소스 수 안정
- teardown 후 dispose 호출

### 12.5 fallback

- WebGL 미지원
- renderer 생성 예외
- 모듈 import 실패
- context lost
- 모델 팩토리 실패

각 경우에 게임 루프가 계속되고 RC2가 표시되어야 한다.

### 12.6 시각 계약 정적 검사

- `#game3d`와 `#game-hud` 계층 및 `pointer-events:none`
- 외부 CDN·외부 모델 URL 없음
- 기능 플래그 없는 일반 배포 모드에서 개발 오버레이 없음
