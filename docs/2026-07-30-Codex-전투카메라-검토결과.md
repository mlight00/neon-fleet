### 구조 검토

- `js/camera-zoom.js`가 배율 상수·클램프·보간·좌표 변환을 순수 함수로 분리했다.
- 카메라 변환은 렌더 좌표와 포인터 역변환에만 사용한다.
- 함선·적·탄환·아이템·월드 이펙트는 같은 transform 안에 있다.
- HUD·배경·컷신·시네마 띠·전체 화면 플래시는 transform 밖에 있다.
- 전체 화면 플래시는 `drawScreen()`, 파티클·텍스트·링은 `drawWorld()`로 분리했다.
- 저장값은 `view.zoom`으로 백필되며 진행 초기화 후에도 보존된다.
- `Ctrl/Cmd+휠`, 입력창 포커스, 키 반복 방어가 있다.
- reduced-motion 사용자는 보간 없이 즉시 목표 배율을 적용한다.
- 일시정지 카메라 버튼은 실제 Chrome 390×844에서 각각 `44×44`, `74×44`, `44×44`였고 영어 접근 가능 이름도 존재했다.
- 실제 Chrome 포털 모드에서 무기 선택 → 전투 진입이 정상이며 콘솔 오류는 0건이었다.

UI/UX 검토 기준인 44px 터치 타깃, 8px 간격, 명확한 포커스, reduced-motion 대응은 충족한다.

## 2. 수정이 필요한 사항

## [P2] 가로 휠도 축소로 처리된다

대상: `js/main.js`의 `wheel` 리스너

현재 분기:

```js
applyZoom(e.deltaY < 0 ? +1 : -1);
```

`deltaY === 0`이면 아래쪽 분기로 들어가 축소된다.

실제 Chrome 재현:

```text
시작 배율: 1.00
deltaX: 40, deltaY: 0
결과 목표 배율: 0.95
```

노트북 터치패드의 가로 스크롤이나 수평 제스처가 카메라 축소로 오인될 수 있다.

필요 조치:

- `deltaY === 0`이면 아무것도 하지 않는다.
- `abs(deltaX) >= abs(deltaY)`인 수평 우세 입력도 아무것도 하지 않는다.
- 이 경우 `preventDefault()`도 호출하지 않는다.
- 실제 이벤트 기반 테스트를 추가한다.

## [P2] 정밀 터치패드의 작은 이벤트가 매번 5%로 계산된다

현재는 `wheel` 이벤트 한 건마다 무조건 5%를 변경한다. 일반 마우스 휠의 한 칸과 정밀 터치패드의 1픽셀 이벤트를 구분하지 않는다.

실제 Chrome 재현:

```text
시작 배율: 1.00
deltaY: -1 이벤트 6회
결과 목표 배율: 1.30
```

정밀 터치패드에서는 한 번의 짧은 손가락 제스처가 여러 이벤트를 발생시키므로 최소에서 최대까지 급격히 튈 수 있다.

필요 조치:

- 수직 delta 누적기를 별도 순수 모듈 또는 테스트 가능한 함수로 만든다.
- `deltaMode`를 픽셀 기준으로 정규화한다.
- 권장 임계값은 50~70px이며, 임계값을 넘을 때만 5% 한 단계를 적용한다.
- 한 이벤트에서 최대 한 단계만 이동한다.
- 방향이 바뀌거나 180~250ms 입력이 없으면 잔여 누적을 초기화한다.
- 전통적인 마우스 휠 `deltaY≈±100`은 한 번에 정확히 한 단계여야 한다.
- 작은 `±1` 이벤트 몇 건만으로는 단계가 바뀌지 않아야 한다.

## [P2] 입력 역변환이 직전 프레임의 카메라 기준점을 사용할 수 있다

현재 프레임 순서:

```text
frame()
  camera.current 보간
  update()
    input.tick()
    squad.update()
  draw()
    camera.anchorX/Y = squad.x/y
```

`input.tick()`은 `draw()`에서 갱신한 직전 프레임의 `anchorX/Y`를 사용한다. 첫 전투 프레임에는 초기값 `(0,0)`을 사용할 가능성도 있다.

대부분의 프레임에서는 오차가 작지만, 고배율에서 빠르게 이동하거나 전투 시작 직후에는 마우스와 함선 목표점이 한 프레임 어긋날 수 있다.

필요 조치:

- `update()`에서 `input.tick()` 직전에 현재 `squad.x/y`를 카메라 기준점으로 동기화한다.
- `draw()`에서도 방어적으로 동기화하거나 공용 `syncCameraAnchor()`를 사용한다.
- 전투 첫 프레임과 빠른 좌우 이동 중 역변환 테스트를 추가한다.

## 3. 증거 보강이 필요한 항목

기존 85/100/130% 스크린샷은 다음 두 가지를 잘 증명한다.

- 플레이어 함대와 링이 배율에 따라 달라짐
- HUD 크기와 위치가 고정됨

하지만 화면에 적·탄환·아이템·파티클이 없어 이 요소들이 함께 확대된다는 시각 증거는 아니다. 소스 구조상 같은 transform 안에 있으므로 구현은 맞을 가능성이 높지만, 출시 후보 검증 자료로는 부족하다.

다음 스크린샷은 같은 전투 상태를 고정해 다시 만든다.

```text
camera-combat-085pct.jpg
camera-combat-100pct.jpg
camera-combat-130pct.jpg
```

각 화면에 반드시 포함:

- 플레이어 함대
- 일반 적 또는 보스
- 플레이어 탄환과 적 탄환
- 코인·크리스탈 등 아이템
- 폭발 파티클 또는 데미지 텍스트
- 고정 HUD
