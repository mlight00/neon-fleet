## 1. 이번 진단의 결론

현재 게임은 전투 중 함대가 커지고 무기·모듈 조합이 달라지는 순간의 재미는 갖추고 있다. 그러나 첫 실패 직후의 보상과 재출격 동선이 약해서, 처음 온 사용자가 재미를 충분히 느끼기 전에 이탈할 가능성이 높다.

실제 새 저장 데이터 기준 관찰값은 다음과 같다.

- 첫 인트로는 5개 패널, 자동 재생 약 19.5초이며 건너뛰기 버튼이 있다.
- 첫 출격은 타이틀 → 시작 무기 선택 → 1회 조작 안내 → 전투 순서다.
- 조작 안내를 이미 본 사용자는 타이틀 → 시작 무기 선택 → 선택지가 하나뿐인 첫 항로 클릭 → 전투 순서다.
- 첫 노드를 완료하고 두 번째 노드에서 사망한 사례의 총 영구 코인은 약 37이었다.
- 가장 싼 격납고 강화는 50코인인 `코인 적립 배수`이고, 전투 체감이 즉시 생기는 강화는 시작 드론 60, 기함 내구도 70, 공격력·연사력 90코인부터다.
- 따라서 기대 가능한 첫 실패 뒤에는 구매할 수 있는 강화가 없고, 사용자는 “실패했지만 다음 판은 더 강하다”는 확신을 얻지 못한다.
- 사망 → 격납고 → 뒤로 이동하면 이전 전투의 기체·적·탄환·HUD가 타이틀 배경에 남는다.
- 모바일 항로는 설명을 보기 위한 첫 탭이 즉시 진입으로 처리되어, 선택 전에 보상과 위험을 이해하기 어렵다.

이번 작업은 아래 네 가지를 함께 해결해야 완료다.

1. 첫 실제 사망 뒤 전투형 영구 강화 1개를 무료로 확정 지급한다.
2. 재출격 때 선택지가 하나뿐인 첫 항로 클릭을 없앤다.
3. 타이틀로 돌아오면 이전 전투 화면을 완전히 정리한다.
4. 모바일 항로를 첫 탭 설명, 두 번째 동작 확정 구조로 바꾼다.

## 3. P0-A — 첫 실제 사망 시 무료 긴급 개조 1회

### 3.1 사용자 경험

저장 데이터당 최초의 실제 사망 결과 화면에 다음 안내를 분명하게 표시한다.

> 첫 원정 지원 · 무료 긴급 개조 1회  
> 실패 데이터를 회수했습니다. 다음 출격부터 영구 적용할 개조를 고르세요.

사용자는 아래 세 가지 중 정확히 하나를 고른다.

| 저장 키 | 사용자 표시 | 실제 효과 |
|---|---|---|
| `drones` | 시작 드론 +2 | `BAL.hangar.upgrades.drones.step`만큼 영구 증가 |
| `hull` | 기함 내구도 +16 | `BAL.hangar.upgrades.hull.step`만큼 영구 증가 |
| `dmg` | 공격력 +0.1 | `BAL.hangar.upgrades.dmg.step`만큼 영구 증가 |

표시 숫자를 UI에 따로 복제하지 말고 현재 밸런스 설정의 `name`, `desc`, `step`, `unit`을 이용한다. 향후 밸런스 수치가 바뀌어도 안내와 실제 효과가 어긋나면 안 된다.

선택 후에는 같은 결과 흐름 안에서 아래를 보여준다.

- 선택한 강화명
- `무료 긴급 개조 완료 · 다음 출격부터 영구 적용`
- 기존 `다시 출격` 버튼
- 기존 `격납고 · 영구 강화` 버튼

무료 개조를 받기 위해 격납고를 반드시 거치게 만들지 않는다. 핵심은 결과 확인 후 바로 재출격할 수 있게 하는 것이다.

### 3.2 정확한 지급 조건

아래 조건을 모두 만족할 때만 제안한다.

- `endExpedition()`의 종료 이유가 정확히 `death`
- 해당 저장 데이터에서 아직 무료 개조를 받은 적이 없음
- 허용된 세 강화 중 최대 레벨이 아닌 항목이 하나 이상 있음

아래 상황에는 절대 지급하지 않는다.

- 일시정지 메뉴의 자발적 `끝내기`
- 캠페인 완료
- 결과 화면 새로고침 또는 뒤로 가기
- 이미 받은 뒤의 두 번째 사망
- 버튼 연속 클릭
- 개발용 화면 진입만으로 발생한 종료

기존 저장 사용자는 과거 사망 여부를 알 수 없으므로, 기능 배포 후 첫 실제 사망에서 1회를 제공한다. 이것은 의도된 동작이다.

### 3.3 저장 구조

`js/save.js`에 아래와 같은 단일 상태를 추가한다.

```js
firstDefeatUpgrade: null
```

허용 값은 다음 네 가지뿐이다.

```text
null | "drones" | "hull" | "dmg"
```

별도의 `claimed` 불리언을 함께 만들지 않는다. 두 필드가 서로 어긋나는 상태를 만들지 않기 위해 선택 키 자체를 지급 완료 상태로 사용한다.

필수 저장 규칙:

- `SAVE_VERSION`을 3으로 올리고 구 저장 데이터를 안전하게 백필한다.
- 구 저장을 여러 번 불러와도 값이나 강화 레벨이 중복 변경되지 않아야 한다.
- 선택 시 최신 `save.get()`을 다시 읽는다.
- 선택 키를 `Set` 또는 동등한 화이트리스트로 검증한다.
- 해당 강화가 최대 레벨인지 다시 확인한다.
- 코인을 차감하지 않는다.
- `up[key] + 1`과 `firstDefeatUpgrade: key`를 한 번의 `save.set()`으로 저장한다.
- 버튼은 첫 입력 즉시 비활성화해 연속 탭을 막고, 저장 쪽에서도 다시 검사한다.
- 전체 데이터 초기화는 무료 개조 기록과 지급된 강화 레벨도 초기화한다. 현재처럼 사운드와 인트로 시청 여부만 보존하는 정책은 유지한다.

### 3.4 결과 정산과 UI 연결

주요 수정 후보:

- `js/main.js`
  - `endExpedition()`
  - 결과 화면을 다시 그리는 작은 헬퍼
  - 무료 개조 자격 계산 및 지급 콜백
- `js/ui.js`
  - `showLose()`
  - 무료 개조 선택 카드 또는 전용 결과 하위 화면
- `js/save.js`
  - 저장 기본값과 마이그레이션
- 필요 시 `js/logic.js`
  - 순수 함수로 분리할 가치가 있는 자격 판정

구현 원칙:

- 기존 코인 정산은 한 번만 수행되어야 한다. 무료 개조 선택 후 결과 화면을 다시 그린다고 `endExpedition()`을 다시 호출하면 안 된다.
- `r.settled`의 기존 중복 정산 방어를 유지한다.
- 결과에 전달할 정산 스냅샷을 한 번 만들고 UI만 다시 그리는 구조를 우선한다.
- `coin`, `magnet`, `cruiser`, `rate`는 첫 무료 선택지에 넣지 않는다.
- 코인 획득량, 격납고 가격, 적 체력, 노드 보상 등 전역 밸런스는 이번 작업에서 바꾸지 않는다.
- 접근 가능한 버튼 이름에는 강화명과 실제 증가량을 포함한다.

### 3.5 완료 조건

- 새 저장에서 첫 실제 사망 후 세 가지 무료 선택지가 보인다.
- 하나를 선택하면 코인은 그대로이고 해당 `up` 레벨만 1 증가한다.
- 다음 출격 생성 시 실제 시작 능력치에 반영된다.
- 선택 후 `다시 출격`을 바로 누를 수 있다.
- 새로고침, 재진입, 재사망, 빠른 연속 클릭으로 두 번 받을 수 없다.
- 전체 초기화 후에는 다시 받을 수 있다.

## 4. P0-B — 재출격 첫 항로 자동 진입

### 4.1 문제

첫 조작 안내를 본 사용자는 매 출격 때 선택지가 하나뿐인 섹터 1 루트 노드를 또 클릭해야 한다. 선택이 아닌 확인 절차여서 재출격 속도만 늦춘다.

현재 핵심 위치는 `js/main.js`의 `enterSectorMap()`이다. 기존에는 첫 출격 안내를 아직 보지 않았을 때만 안내 완료 후 루트 노드로 바로 들어간다.

### 4.2 요구 동작

- 최초 사용자:
  - 시작 무기 선택
  - 기존 1회 조작 안내 표시
  - `전투 시작`을 누르면 섹터 1 루트 노드 자동 진입
- 안내를 이미 본 사용자:
  - 시작 무기 선택
  - 섹터 1 루트 노드 자동 진입
  - 별도의 항로 화면이나 클릭 없음
- 섹터 1의 첫 노드 이후:
  - 현재처럼 갈림길 항로 화면 표시
- 섹터 2 이상 진입:
  - 현재처럼 항로 화면 표시
- 선택 가능한 노드가 둘 이상인 상황:
  - 절대 자동 선택하지 않음

권장 가드는 의미가 드러나게 작성한다.

```text
sector === 1
done.length === 0
current node가 없음
첫 열의 진입 가능한 루트가 정확히 1개
```

첫 안내를 보지 않은 경우에는 기존 안내를 먼저 보여주고, 안내 완료 콜백에서 같은 루트로 진입한다. 안내를 이미 본 경우에만 즉시 진입한다.

### 4.3 완료 조건

- 새 사용자 안내는 여전히 정확히 한 번 나온다.
- 첫 출격과 모든 재출격에서 섹터 1 첫 항로 클릭이 사라진다.
- 첫 노드 완료 뒤의 갈림길은 유지된다.
- 다음 섹터의 맵과 보스 경로는 자동 선택되지 않는다.
- 키보드·마우스·터치 출격 흐름이 모두 멈추지 않는다.

## 5. P0-C — 타이틀 전투 잔상 완전 제거

### 5.1 문제

`showTitleScreen()`은 타이틀 오버레이를 띄우지만 이전 `run`을 비우지 않는다. 그 결과 사망 → 격납고 → 뒤로 이동하면 죽은 함대, 적, 탄환, HUD 등이 타이틀 뒤에 남는다.

`draw()`은 `run`이 있으면 전투 개체와 HUD를 그리므로, CSS로 일부를 가리는 방식이 아니라 게임 상태를 정상 종료해야 한다.

### 5.2 요구 동작

타이틀로 이동할 때 한 곳에서 다음 상태를 정리한다.

```text
state = "title"
run = null
drafting = false
betweenStages = false
paused = false
input.active = false
input.charging = false
입력 skip latch 정리
```

별도 `resetToTitleState()` 같은 작은 헬퍼를 두고 `showTitleScreen()` 진입 시 호출하는 방식을 권장한다. 이름은 달라도 되지만 여러 경로가 같은 정리 로직을 사용해야 한다.

검증해야 할 타이틀 진입 경로:

- 첫 로드
- 인트로 완료 후
- 결과 → 격납고 → 뒤로
- 타이틀 → 격납고 → 뒤로
- 일시정지 → 끝내기
- 데이터 초기화 완료 또는 취소

### 5.3 금지사항

- 타이틀 오버레이의 불투명도만 높여 잔상을 숨기지 않는다.
- 전투 캔버스 전체를 `display:none` 처리하지 않는다.
- 타이틀 진입 과정에서 이미 완료된 코인 정산을 다시 수행하지 않는다.
- 오디오 설정 패널과 인트로 재생 버튼을 망가뜨리지 않는다.

### 5.4 완료 조건

- 타이틀에서는 별 배경과 정상 타이틀 연출만 보인다.
- 함대, 적, 보스, 탄환, 코인, 전투 HUD, 내구도 바, 일시정지 버튼, 차지 버튼이 남지 않는다.
- 타이틀에서 다시 출격하면 새 `run`이 정상 생성된다.

## 6. P0-D — 모바일 항로 첫 탭 설명, 두 번째 동작 확정

### 6.1 문제

현재 `js/ui.js`의 `showSectorMap()`은 마우스 `mouseenter`와 키보드 `focus`에서 설명을 보여주지만, 터치 `click`은 바로 `onPick()`을 실행한다. 모바일 사용자는 항로의 위험과 보상을 확인하기 전에 진입한다.

### 6.2 기기별 요구 동작

#### 마우스가 있는 데스크톱

- 마우스 오버: 기존처럼 설명 표시
- 한 번 클릭: 기존처럼 즉시 항로 확정
- 마우스가 떠나면 임시 설명 숨김

#### 키보드

- 포커스 이동: 설명 표시
- Enter 또는 Space: 한 번에 항로 확정
- 현재 `attachKeyNav()` 동작을 깨지 않음

#### 터치 또는 coarse pointer

- 첫 탭: 해당 노드를 선택 상태로 만들고 설명과 보상을 고정 표시
- 첫 탭만으로 `onPick()`을 호출하지 않음
- 다른 노드를 탭하면 선택 상태와 설명만 변경
- 같은 노드를 두 번째 탭하거나, 아래의 명확한 `이 항로로 진격` 버튼을 누르면 확정
- 확정 버튼에는 선택한 노드 종류가 포함된 접근 가능한 이름을 부여

### 6.3 UI 세부 규칙

- 기존 44×44px 노드 터치 영역을 줄이지 않는다.
- 선택된 노드는 색, 테두리, 발광 중 두 가지 이상으로 명확히 구분한다.
- `aria-pressed` 또는 동등한 선택 상태를 갱신한다.
- 같은 종류의 노드가 여러 개여도 접근 가능한 이름이 중복되지 않게 열·행 또는 순번을 포함한다.
- 예시: `정예 전투, 3열 2번째 항로, 코인 +80%, 모듈 4택`
- 모바일 설명은 떠다니는 툴팁만 사용하지 말고 지도 아래의 고정된 정보 영역에도 표시한다. 화면 가장자리 잘림을 방지하기 위함이다.
- 터치 선택 전 확정 버튼은 숨기거나 비활성화한다.
- 지도 토폴로지, 노드 생성 확률, 보상 수치는 변경하지 않는다.
- 안내 문구는 실제 조작에 맞게 데스크톱과 모바일을 구분한다.

### 6.4 구현 주의

- `click` 이벤트만 보고 모든 기기를 coarse pointer로 판단하지 않는다.
- `PointerEvent.pointerType`, 최근 `pointerdown`의 종류, `matchMedia('(pointer: coarse)')`를 조합하되 키보드 확정을 터치로 오인하지 않는다.
- 같은 노드의 두 번째 탭과 확정 버튼이 거의 동시에 들어와도 `onPick()`은 한 번만 실행되게 로컬 확정 가드를 둔다.
- 맵을 다시 열 때 이전 맵의 선택 상태가 남으면 안 된다.

### 6.5 완료 조건

- 모바일 첫 탭으로 노드 진입이 일어나지 않는다.
- 설명에는 노드 이름과 보상·위험 정보가 읽기 쉽게 표시된다.
- 같은 노드 두 번째 탭 또는 확정 버튼으로 한 번만 진입한다.
- 데스크톱 한 번 클릭과 키보드 한 번 확정은 기존대로 동작한다.
- 가로 스크롤과 화면 밖 잘림이 없다.

## 7. 자동 테스트 필수 목록

기존 458개 테스트를 모두 유지하고 아래 회귀 테스트를 추가한다. 단순히 소스 문자열이 존재하는지만 보는 테스트보다, 저장 상태와 콜백 결과를 검증하는 행동 테스트를 우선한다.

### 7.1 저장 및 무료 개조

1. 구 버전 저장을 불러오면 `firstDefeatUpgrade`가 `null`로 백필되고 `SAVE_VERSION`이 3이 된다.
2. 같은 구 저장을 여러 번 불러와도 강화 레벨이 변하지 않는다.
3. 새 저장의 첫 `death`에서만 무료 선택 자격이 생긴다.
4. `quit`과 캠페인 완료는 무료 선택 자격을 만들지 않는다.
5. `drones`, `hull`, `dmg` 중 하나를 고르면 그 레벨만 정확히 1 증가한다.
6. 무료 선택 전후 코인 값이 동일하다.
7. 허용되지 않은 키는 거부된다.
8. 최대 레벨 항목은 선택할 수 없다.
9. 연속 호출, 새로고침을 가정한 재호출, 두 번째 사망에도 추가 지급되지 않는다.
10. 전체 초기화 후 `firstDefeatUpgrade`와 `up`이 기본값으로 돌아온다.

### 7.2 출격 흐름

11. 첫 안내를 보지 않은 새 저장은 안내를 한 번 표시한 후 섹터 1 루트로 진입한다.
12. 안내를 본 저장은 섹터 1 첫 루트로 바로 진입한다.
13. 섹터 1 첫 노드 완료 후 갈림길은 자동 선택하지 않는다.
14. 섹터 2 이상 첫 맵도 자동 선택하지 않는다.
15. 루트가 한 개가 아닌 비정상 입력에서는 자동 선택하지 않는다.

### 7.3 타이틀 상태

16. 타이틀 진입 시 `run === null`이고 플레이·드래프트·일시정지 상태가 정리된다.
17. 타이틀 렌더에서 전투 HUD와 개체 렌더 경로가 실행되지 않는다.
18. 타이틀 정리 후 새 출격이 정상 시작된다.

### 7.4 항로 입력

19. coarse pointer 첫 탭은 미리보기만 바꾸고 `onPick()`을 호출하지 않는다.
20. 같은 노드 두 번째 탭 또는 확정 버튼은 `onPick()`을 정확히 한 번 호출한다.
21. 다른 노드 첫 탭은 선택만 바꾼다.
22. 마우스 클릭과 키보드 Enter·Space는 기존처럼 한 번에 확정한다.
23. 여러 항로 버튼의 접근 가능한 이름이 고유하다.

테스트 파일명은 기존 저장소 규칙에 맞추되, 예시는 다음과 같다.

## 13. 최종 완료 정의

아래 문장을 모두 참이라고 입증해야 작업 완료다.

- 처음 사망한 사용자는 코인이 부족해도 전투 체감형 영구 강화 하나를 얻는다.
- 그 강화는 다음 출격에서 실제로 적용되고 두 번 받을 수 없다.
- 사용자는 결과 화면에서 바로 다시 출격할 수 있다.
- 재출격 시 선택지가 하나뿐인 첫 항로를 다시 누르지 않는다.
- 타이틀로 돌아오면 이전 전투의 어떤 시각 요소도 남지 않는다.
- 모바일 사용자는 항로 설명을 읽고 나서 확정할 수 있다.
- 데스크톱 마우스와 키보드 조작은 이전보다 느려지지 않는다.
- 기존 자동 테스트와 신규 테스트가 모두 통과한다.
- 데스크톱·모바일 브라우저 증거가 남아 있다.
- `master` 병합과 GitHub Pages 배포는 하지 않았다.

이 중 하나라도 입증하지 못하면 완료가 아니라 미완료 또는 제한 사항으로 보고한다.
