### §4-1 단일 투영 계약 (P0-1) — 완료
한 프레임에 투영이 **두 번** 만들어지고 있었다. `update()` 시작(입력 처리 **전**)에서 한 번,
`draw()`에서 또 한 번. 그래서 조준 역변환은 **움직이기 전** 기함 위치를, 그림은 **움직인 뒤**
위치를 썼다. Codex D-2 가 지적한 어긋남의 실체가 이것이었다.

- `update()` 시작 = 첫 프레임 부트스트랩만
- `update()` **끝** = 투영 확정 1곳 (월드 갱신이 모두 끝난 뒤)
- `draw()` = 만들지 않고 확정된 스냅샷을 **공유**

### §4-3 차지빔 유한 끝점 + 잔광 제거 — 완료
빔 길이를 눈대중 상수(`LANCE_LEN = 1400`)에서 **world y=0 까지의 실제 깊이**로 바꿨다.
발사체 깊이 규칙에서 그대로 나온다: `shotDepth(sqy,0) − shotDepth(sqy,sqy) = sqy · SCALE_Z`.
→ 빔 끝이 **발사체가 world y=0 에 있을 때 놓이는 바로 그 자리**에 온다. 같은 규칙, 같은 그림.

그리고 `drawLanceAfterglow` 를 **삭제**했다. §G-31 의 전제("world y=0 은 소실점 너머라 빔이 못 닿는다")가
finite top plane 계약(§4-1)에서 거짓이기 때문이다 — world y=0 은 **화면 안**에 있다.

> ⚠️그 잔광은 애초에 틀린 그림이었다(Codex G-2[중대]). 월드 x 를 **화면 x 로 그대로** 썼다:
> `c.fillRect(e.x - w/2, ...)`. 추적 모드에서 둘은 다르다. 기함 x=420 에서 **104.4px** 어긋났고
> 폭도 월드 63px 을 그대로 써 투영값 30.49px 의 2배였다. "판정 범위를 보여주는 표시"가
> 실제 판정과 다른 자리를 가리키고 있었다.

**화면상 결과**(480×800, zoom 2.2 실측): 빔이 기함 y=664 → **y=120** 까지, 화면 세로의 68% 관통.
옛 고정값은 소실점(y≈184)에 수렴했으므로 **오히려 더 위까지** 간다 — §G-30 "차지샷이 너무 짧다"도 함께 해소된다.

검증 2건 추가: `G34-LANCE-FINITE`(길이식이 `shotDepth` 두 호출의 차이와 일치, t·sqy 9조합) ·
`G34-LANCE-NO-AFTERGLOW`(끝점이 화면 안·유한).

### §7 (P0-4) 발사 원점 보정을 모든 렌더 경로에 — 완료
§G-28 에서 만든 `SHOT_ORIGIN` sidecar 가 **2D 직접 경로에만** 적용돼 있었다(Codex G-1[중대]).
같은 탄이 경로마다 다른 자리에서 나오고 있었다.

**진단**: 보정을 "그리기 좌표계에서 `translate`"로 했던 것이 원인이다. 보정량은 **월드 px** 인데
2.5D 는 그 위에 `scale` 을 곱해 둔 좌표계라 보정까지 함께 확대됐다(실측 11.44px 과보정).

**해법**: 보정은 **투영 입력의 월드 x** 에 넣는다 — 그러면 화면 환산은 투영이 한다.
§4-1 의 "화면 위치는 단일 투영이 정한다"와 같은 원칙이다.

| 경로 | 이전 | 이후 |
|---|---|---|
| 2D 직접 (`Bullet.draw`) | translate(odx) — 월드=화면이라 우연히 맞음 | 그대로(상쇄 처리) |
| 2.5D (`drawProjected`) | translate 가 scale 과 곱해져 **11.44px 과보정** | 투영 입력 보정 + 내부 이중분 상쇄 |
| 레이저 (`drawLaserStreak`) | **보정 0**(이 경로만 빠져 있었다) | 같은 규칙으로 보정 |
| 3D 수집 (`main`) | sidecar 를 **읽지도 않음** | `shotRenderX(b)` 로 투영 입력 보정 → `o.sx` 경유로 3D 배치까지 반영 |

**같이 고친 것 하나**: `shotOriginDX` 가 읽으면서 WeakMap 에서 **지우고** 있었다.
한 프레임에 여러 경로가 같은 탄을 읽는 구조로 바뀌면 첫 호출만 보정을 받고 나머지는 0 을 받는다.
→ **순수 조회**로 바꿨다(WeakMap 이라 탄이 죽으면 함께 사라져 지울 이유도 없다).

> ⚠️처음엔 `chase-render.js` 가 `entities.js` 를 직접 import 했는데 **경계 규칙 위반**이었다(CW2-27:
> 렌더 계층은 `chase-camera.js` 외 전투 모듈을 몰라야 한다). → **의존성 주입**으로 바꿨다.
> `drawWorldProjected(..., { shotOriginDX })` 한 줄이 그 접점이다.

검증 4건 (`tests/g34-shot-origin.test.mjs`) — 전부 실행 기반:
`G34-ORIGIN-PURE`(반복 조회 값 고정) · `G34-ORIGIN-25D`(zoom 2 × 기함위치 3 에서 화면 x 가 투영값과

### §5 (P0-2) 카메라 중심 가로식 + 동적 데드존 — 완료
**이사님 아이디어의 본체다.** 기함이 좌/우 경계를 넘으면 그쪽 가려졌던 영역이 점진적으로 드러난다.

**왜 기존 방식으로는 안 됐나**: 예전 가로식은 `followFrac`(0.42) 부분 추종이었다.
`centerX + (squadX−centerX)·f + (x−squadX)·L` 를 카메라 형태로 정리하면 실효 카메라 위치가
`squadX − (squadX−centerX)·f/L` 인데, **L(가로배율)은 깊이마다 다르다** —
한 프레임에 카메라가 깊이별로 여러 곳에 있는 셈이라, 카메라를 실제로 붙잡아 두는 데드존과 공존할 수 없다.
→ `followFrac` **폐기**. 가로식을 카메라 중심으로 바꿨다:

```
chaseX = centerX + (worldX − cameraWorldX) · lateral(depth) · zoom
```

**데드존 동작** (`updateChaseCameraX`, 순수 상태 함수):
- 데드존 **안** — 카메라 고정. 기함이 화면에서 1:1로 움직인다(조종감은 오히려 더 좋아진다).
- 데드존 **밖** — 카메라가 넘어간 만큼만 따라간다. 그쪽 영역이 드러난다.
- 히스테리시스 6px(경계 떨림 방지) · dt 기반 감쇠(τ=0.12s, 프레임률 무관) · 월드 밖 비추지 않기.
- 수명 경계: 전술 구간(`chaseBlend=0`)에서는 카메라를 기함에 붙여 둔다 → 추적 전환 시 튀지 않는다.

**동적 데드존**: `deadHalf = max(0, visibleHalfWorld − squadMargin)`,
`squadMargin = BAL.squad.laneMargin(30) + SHIP_DEFS[tier].visualWidth × 0.4`.
줌·기함 등급이 바뀌면 데드존도 따라 바뀐다.

**브라우저 실측**(480×800, zoom 2.2 — 보이는 반폭 87.3, 데드존 41.3):

| 상황 | 기함 x | 카메라 x | 한계 |
|---|---|---|---|
| 왼쪽 끝 | 64 | **102.1** | 87.3 이상 ✓ |
| 오른쪽 끝 | 416 | **377.9** | 392.7 이하 ✓ |

카메라가 "기함 ∓ 데드존"에 정확히 수렴하고 트랙 밖을 비추지 않는다.
기함이 데드존 안으로 돌아오면 카메라는 그 자리에 멈춘다(240 → 201.4 에서 정지 확인).

검증 9건 (`tests/g34-deadzone.test.mjs`): HOLD · FOLLOW · HYST · DT(30/60/144fps 동일) ·
CLAMP · WIDE · MARGIN · **INVERSE**(줌 4 × 기함 3 × 카메라 5 × 화면점 5 = 300조합 왕복 ≤0.01px) · CAMCENTER.
`CH-07` 은 새 계약(데드존)으로 다시 썼다 — 뜻은 그대로다(이동이 보이고, 잘리지 않는다).

> ⚠️**부수 사실 하나**: 실제 줌 범위(1.0~2.2) 어디서도 트랙 전체가 화면에 들어오지 않는다
> (`nearLateral=1.25` 가로 확대 때문에 보이는 반폭이 최대 192 < 트랙 반폭 240).
> 즉 **데드존은 항상 의미를 갖는다** — 무엇을 보여줄지 늘 골라야 한다.

### §6 (P0-3) 가장자리 경고 확대 + 스크롤 정책 확정 — 완료
데드존(§5)이 들어오면서 화면 밖에 남는 영역이 늘었다. 그 뒤처리 두 가지다.

**① 원거리 공격형 6종을 경고에 추가**
예전엔 충돌형(Creature·Charger·Bomber·Meteor·Mine·Blinker)만 경고했다.
Sniper·Turret·Weaver·Zapper·Shielder·BroodCarrier 는 **화면 밖에서도 나를 쏜다** —
부딪히지 않아도 위험하므로 뜻이 다르다. 새 종류 `shooter` 로 분리했다.

| 위협 | 색 | 모양 | 점수 대역 |
|---|---|---|---|
| 보스 | 빨강 `#ff5a6a` | 삼각형(채움) | 100000 |
| 적탄 | 주황 `#ff8a3c` | 원 | 50000 |
| **사격형(신규)** | **보라 `#c98cff`** | **마름모** | **30000** |
| 충돌형 | 노랑 `#ffb020` | 사각 | 20000 |

색과 모양을 **둘 다** 달리했다(색만으로 나누면 색각 이상에서 구분이 사라진다 — §9 원칙).
사격형이 충돌형보다 앞선다: 사거리가 화면보다 길어 "저기 있다"를 아는 것이 충돌 예고보다 먼저다.

**② 가장자리 스크롤 정책 = B (명시적 결정)**
기함이 트랙 끝에 닿았을 때 두 갈래가 있었다.

- (A) 카메라가 기함을 계속 따라간다 → 화면 절반이 **트랙 밖 빈 공간**
- (B) 카메라를 트랙 안쪽 한계에서 멈춘다 → 기함이 화면 중앙을 벗어난 채 보인다

**B를 택했다.** 빈 공간에는 적도 픽업도 없어 정보가 0이고, 좁은 세로 화면에서 절반을 버리는
대가가 너무 크다. B에서 기함이 중앙을 벗어나는 것은 오히려 "지금 끝에 붙어 있다"는 위치 정보가
된다 — 데드존이 이미 같은 원리로 동작하므로 감각도 일관된다.
→ **화면에 보이는 것은 항상 유효한 월드다.**

검증 6건 (`tests/g34-edge-warn.test.mjs`): SHOOTER(6종 전부) · KINDS(충돌≠사격) ·
ONSCREEN(남발 방지) · CAMERA-AWARE(카메라 이동에 따라 대상이 바뀜) ·
**POLICY**(zoom 3종에서 화면 양끝이 가리키는 월드 x 가 트랙 [0, 480] 안) · POLICY-SHIP.

> ⚠️테스트를 짜다 한 번 걸렸다: 적 클래스 생성자 시그니처가 제각각이다
> (`Sniper(x)` · `Turret(x,y)` · `Weaver(fromLeft, logicalW)` · 나머지는 `(x)` 에 y=−30 고정).
> 생성자에 묶인 테스트는 생성자를 손볼 때마다 깨지므로 **만든 뒤 위치만 직접 지정**하도록 바꿨다.

## 기함 2D 문제 — 원인 규명·수정 완료 (2026-08-11 밤, 이사님 콘솔 캡처로 발견)

### 원인: 제가 §7에서 만든 크래시

이사님이 F12 콘솔을 캡처해 주셔서 한 줄로 드러났다.

```
[chase3d] 렌더 예외 → 이 세션은 2D 로 고정:
ReferenceError: camOriginDepth is not defined
    at placeShots (chase3d-renderer.js:603:51)
    at Object.frame (chase3d-renderer.js:833:11)
```

`placeShots` 안에서 `camOriginDepth` **선언이 통째로 빠져 있었다**(§7 작업 중 유실).
첫 프레임에 `ReferenceError` → 렌더러가 "이 세션은 2D 로 고정" 폴백 → **3D 가 아예 안 뜬다.**
기함이 2D 로 보인 것은 물론이고, 이 세션의 3D 발사체·적·픽업이 전부 2D 로 돌아가 있었다.

`__NF.chase3dInfo()` 가 계속 `null` 을 뱉은 것도 같은 이유였다 — 저는 그걸 "pane 숨김 탓"으로
읽었지만 **실제로는 렌더러가 죽어 있었다.** 잘못된 가정이었다.

### 수정
`placeShots` 에 선언 복구(`placeSwarm` 에는 남아 있었다 — 두 함수 중 한쪽만 유실됐다):
```js
const camOriginDepth = ctl._camOriginDepth > 0 ? ctl._camOriginDepth : CAMERA.chase.dist;
```

### 왜 946개 테스트가 이걸 못 잡았나
`ReferenceError` 는 **그 줄이 실제로 실행될 때만** 난다(파싱은 통과). 그런데 어떤 테스트도
`chase3d-renderer` 의 `frame()` 을 돌리지 않았다 — WebGL 이 필요해서다.
→ `G34-RENDERER-NO-UNDEF` 추가(모듈 실제 import + `camOriginDepth` 선언/사용 대응 확인).
   ⚠️이건 임시방편이다. **THREE mock 으로 `frame()` 을 실제로 돌리는 테스트가 있어야 근본 대책이다.**

**검증: 946 / 946 통과.** 실제 3D 표시 여부는 이사님 실기 확인 필요.

## A안 적용 — 첫 전환 깜빡임 제거 (2026-08-11 밤)

이사님이 **A안(유휴 프리페치)** 을 선택하셨다.

### 문제
`INIT_ZOOM` 이 3D 가 **보이기 시작하는 배율과 같았다**(둘 다 2.00). 줌 단계가 100/150/200/220 으로
점프하므로 "200% 를 요청한 순간 로드 시작"의 실제 여유는 줌 애니메이션 수백 ms 뿐이고,

### 해법
`shouldPrefetch3D(zoomTarget) = zoomTarget > 1.0` — **확대를 한 번이라도 누르면** 유휴 콜백
(`requestIdleCallback`, 없으면 짧은 타이머)으로 3D 자원을 미리 받아둔다.

| 배율 | 받는가 | 표시하는가 |
|---|---|---|
| 100% | ✗ | ✗ |
| 150% | **○ (유휴 시간에 미리)** | ✗ |
| 200%+ | ○ (즉시) | ○ |

⚠️100% 로만 노는 플레이어는 여전히 아무것도 받지 않는다 — 예전 G21 이 150% 전용 플레이어에게
20MB 를 지웠던 문제(Codex P0)의 취지를 그대로 지킨다.

### 브라우저 실측
150% 로 올린 뒤 4초 → `{hero:true, available:true, degraded:false, zoom:1, t:0}`
= **준비는 끝났고 표시는 아직 안 한다.** 200% 로 올리는 순간 곧바로 3D 가 나온다.

### 부수: 소스 문자열 대조가 또 깨졌다 (다섯 번째)
`C3D-visual-layers` 가 3D 요청 게이트를 정규식 한 줄로 대조하고 있었다. 계약은 멀쩡한데
프리페치 분기를 추가하면서 형태가 바뀌어 실패했다 → **조건 4개가 다 있는지** 확인하는 방식으로 교체.
(§G-27 · §G-30 · §G-34 HW-16 · AS-04 에 이은 다섯 번째. 남은 대조도 발견 즉시 같은 방식으로 바꾼다.)

→ "타이틀·무기 선택에서는 #game3d 가 생기지 않는다" 계약(C3D-visual-layers) 그대로.

### 타이틀 캔버스 금지 해제 (이사님 결정 2026-08-11)

이사님 질문: "타이틀에서 캔버스를 미리 만들지 않는다는 규칙은 왜 만든 거야?"

**규칙의 근거를 확인했다.** §G-21 완료보고서 원문:
> "더 일찍 잡으면 **100%만 노는 플레이어에게도 GLB를 지우고**, 경계를 START_ZOOM 과 같게 두면 첫 프레임이 빈다"

즉 취지는 **"3D 를 안 쓸 사람에게 비용을 지우지 마라"** 였다.
그런데 지금 프리페치 조건은 이미 `shouldPrefetch3D` = **확대를 눌렀다(100% 초과)** 다.
그 사람은 3D 를 쓸 사람이므로 **원래 취지를 해치지 않는다.** → 이사님 판단대로 캔버스도 미리 만든다.

**왜 네트워크만 데우는 것으로는 부족했나**: WebGL 컨텍스트 생성·셰이더 컴파일·GLB 파싱·GPU 업로드는
**캔버스가 있어야 시작된다.** 모듈·GLB 를 미리 받아도 그 뒤 단계가 남아 5초가 걸렸다.

**브라우저 실측**(타이틀에서 220% 설정 후 7초):
```
state: title
캔버스생성: true   캔버스보임: opacity 0 / visibility hidden
준비됨: { hero: true, available: true, degraded: false }
```
캔버스는 만들어졌지만 **화면에는 나타나지 않고**(`opacity:0`), 렌더러는 준비 완료다.

**원래 취지는 테스트로 잠갔다**: `G34-PREFETCH-SCOPE` — `shouldPrefetch3D(1.0) === false`.
이 줄이 "100% 전용 플레이어에게 비용 0"의 최후 방어선이다.

**검증: 948 / 948 통과.**

### 시작을 2D로 고정 + 준비 후 복원 (이사님 제안 2026-08-11)

이사님 제안: "무조건 시작은 2D로 하고, 그동안 3D를 로딩해서, 확대하는 순간 제대로 3D가 뜨게."

**문제의 진짜 뿌리**: 저장된 배율(220%)이 **페이지를 열자마자 복원**되고 있었다
(`createCamera(save.get().view?.zoom)`). 그래서 3D 준비가 끝나기 전에 이미 추적 모드였고,
프리페치를 아무리 앞당겨도 "복원 시점 < 준비 완료 시점"인 한 해결되지 않았다.

**구현**
- `createCamera(undefined)` — 시작은 **항상 100%(2D)**
- 저장값은 `_restoreZoom` 에 보관(저장소 자체는 안 건드린다 — 다음 세션에도 그대로)

### "큰 기함이 스친다" 근본 수정 — GLB 준비 전에는 2D 유지

원인: `flagshipLayer` 게이트가 **렌더러 준비**만 봤다. 기함 GLB 는 그 뒤에 **비동기로** 온다

### 큰 기체 스침 — 진짜 원인은 **2D·3D 가 동시에 켜져 있던 것**

이사님: "5초 기다리면 큰 기체가 안 나오는데, 시작하고 **바로** 220%로 바꾸면 스쳐 나온다."

숨겨도 기함이 사라지지 않는다. 오히려 "한 척만 보이는" 올바른 그림이 된다.

## 공통 룰 확정 — 출격은 언제나 100%(2D)로 시작 (이사님 결정 2026-08-11)

> "출격하기 누르면 마지막 전술 시점을 불러오는 게 아니라 그냥 100% 2D 모드로 시작하도록 하자."

**왜 룰로 못 박는가**: 저장 배율을 복원하면 **3D 준비가 끝나기 전에 이미 추적 모드**가 되어

**적용**: `startPlay()` 초입에서 `camera.target = DEFAULT_ZOOM`.
페이지 로드뿐 아니라 **출격할 때마다** 적용된다(출격 종료 후 재출격 포함).

**저장은 계속한다** — "복원하지 않는다"와 "저장하지 않는다"는 다르다.
저장값은 `_restoreZoom` 이 읽어 **3D 프리페치 신호**로 쓴다(220% 를 쓰던 플레이어를 미리 준비시킨다).
