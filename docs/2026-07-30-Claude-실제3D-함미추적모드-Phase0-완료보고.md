## 1. 구현 요약

현재 2.5D 함미 추적 시점(RC2)의 “1980년대식 가짜 입체감”을 보완하기 위해, **기존 2D 게임 규칙은 전혀 바꾸지 않고** 대표 기함과 대표 적·보스·게이트·투사체를 **실제 3D 형상·원근·조명**으로 렌더링하는 선택형 시제품을 만들었습니다.

- Three.js(r160, WebGL) 를 **로컬 벤더링**해 `?chase3d=1`에서만 동적 로드. 플래그가 없으면 three 자체를 내려받지 않음.
- 게임의 진실은 계속 2D(위치·충돌·판정·스폰·보상·RNG·저장). 3D는 그 상태를 **읽어서 같은 순간을 3D로 보여주는 렌더러**일 뿐.
- 100~160% 기존 표시 → 160~200% 교차 전환 → 200~220% 실제 3D 함미 추적. 실패·미지원·컨텍스트 손실 시 즉시 현재 RC2로 복귀(빈 화면 없음).
- 3캔버스 계층(#game 2D / #game3d WebGL / #game-hud HUD)으로 HUD가 3D에 가려지지 않음.

## 4. 2D 상태와 3D 동기화 방식 〔코드〕〔자동〕

좌표 계약(§8):

```
X = (worldX - squadX) * SCALE_X   // 플레이어 상대 가로(기함은 항상 X=0)
Z = (squadY - worldY) * SCALE_Z   // 진행 방향(앞쪽 +Z, 카메라에서 멀어짐)
Y = visualAltitude                // 시각용 높이. 충돌 판정엔 절대 미사용
```

- 매 프레임 `buildSnapshot(run)`(읽기 전용) → `computeSceneModel(snap)`(순수) → `scene.apply()` → `render()`.
- 기존 `worldX/worldY` 는 3D용으로 수정하지 않음. 게이트 3D 레인 경계는 `laneRect(i)`(실제 판정 좌표)를 그대로 투영 → **표시 == 판정**.
- 레이저·랜스의 3D 발사점은 실제 공격 주체(기함 함미)에 붙음.

## 7. 600프레임 A/B 상태 비교 결과 〔자동〕+〔코드〕

3D는 살아있는 상태를 **읽기만** 하므로 on/off 로 2D 시뮬레이션이 갈라지지 않는다. 이를 대체 객체 추정이 아니라 **실제 sync 경로**로 확인:

- 〔자동〕`chase3d-determinism`: 같은 입력으로 600프레임 전개. 매 프레임 A(3D sync 호출)와 B(미호출)의 **2D 상태 지문(기함 위치·체력·적 위치/생존·투사체) 완전 동일**, 그리고 A 는 sync **전후 지문 불변**. 추가로 `deep-freeze` 한 world 로 sync 통과 시 **예외 0**(쓰기 시도가 있으면 freeze 가 throw) → 쓰기 0 증명.
- 〔코드〕`chase3d.frame` 은 `draw()`(렌더 단계)에서만 호출되고 `update(dt)` 본문엔 없음(정적 검사). → 게임 진행 경로에 3D가 개입하지 않음.

결론: 3D on/off 의 실제 2D 게임 상태·RNG 진행이 동일(§16 “600프레임 상태가 다름” 회피).

## 14. 알려진 한계

1. **실 sustained FPS 미측정** — 검증 환경 rAF 정지(§9 참조). 렌더 비용(≤1.33ms)으로 60fps 여유를 추정. 실기기 확인은 개발 오버레이로.
2. **2d-100 / transition-180 스크린샷은 항로 선택(track) 페이즈** 함대·배경 기준 — 라이브 전투 적 스폰은 UI 항로 확정이 필요해, 3D 형상 증거는 결정적 검증 장면(§11)에서 확보. 캠페인 실전에서도 200% 이상 확대 시 동일 3D 표시.
3. **게이트 3D는 레인 경계 기둥(최소 표현)** — 판정 위치엔 정확히 일치하나, 향후 통과 아치·바닥 발광 등 가독성 강화 여지.
4. **전환 중(0<t<1) 2D 월드는 3D 아래로 디졸브**(3D 캔버스 opacity=t). 양 끝(100%·220%)은 정확하며, 중간 구간은 완전한 알파 교차페이드가 아닌 근사.
5. B1 등 일부 모델은 매우 단순한 저폴리(의도적, §4.3 “충분하면 더 적게”).
6. 그림자·블룸·포스트프로세싱 없음(Phase 0 금지 항목, 의도적).

## 15. 전체 3D 확장 시 예상 대상 수·용량·작업량

- **대상 수:** 기함 6종 + 일반 적 12종 + 보스 10종 + 드론·순양함·게이트·투사체·픽업 ≈ **28종 이상**.
- **용량:** Three.js 0.64MB 고정. 모델은 코드 지오메트리(텍스처 0)라 종당 수~수십 KB → 28종 확장해도 추가 **~0.2~0.5MB** 예상(전체 <46MB, 50MB 여유 충분). 고품질 GLB 도입 시 종당 수백KB~수MB로 커지므로 **선택적**.
- **작업량:** 종당 모델 팩토리·재질·변주 0.5~1일 → 28종 **≈ 3~5주(1인)**. Phase 0에서 만든 부품(엔진·날개·장갑·무장)·색상 설정 분리 덕에 H0~H5·적 계열은 재사용으로 가속.
- **선결:** 본 Phase 0 승인 관문 통과가 조건. 승인 전 전체 3D 제작 착수 안 함.
