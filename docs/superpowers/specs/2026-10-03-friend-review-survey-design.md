# 친구 테스트 리뷰 설문 — 설계서 (2026-10-03, 이사님 결정)

## 목적
연휴(10/3~10/5) 동안 단톡방 친구들이 스타포지 러시를 해 보고, 게임이 끝나면 그 자리에서 짧은 설문을 보내게 한다.
응답은 자동으로 한곳에 쌓여 이사님과 내가 바로 본다. 친구들의 실제 진행 기록은 난이도 보정 근거로도 쓴다
(난이도 판단 기준은 실플레이 — 봇 판단 금지 규칙과 같은 방향).

## 설문 문항(게임 화면과 구글 설문지가 한 글자도 같아야 한다)
| 키 | 문항 | 종류 | 값 | 게임에서 필수 |
|---|---|---|---|---|
| fun | 재미있었나요? | 별 1~5 (설문지: 선형 배율 1~5, 1=별로 · 5=최고) | `1`~`5` | 예 |
| diff | 난이도는 어땠나요? | 하나 고르기 | 너무 쉬움 / 조금 쉬움 / 딱 좋음 / 조금 어려움 / 너무 어려움 | 예 |
| again | 또 하고 싶나요? | 하나 고르기 | 또 할래요 / 가끔 할 것 같아요 / 이번으로 충분해요 | 아니오 |
| best | 제일 좋았던 것 하나 | 하나 고르기 | 부대가 커지는 맛 / 게이트 고르기 / 보스전 / 무기 바꾸기 / 스토리 그림 / 잘 모르겠어요 | 아니오 |
| note | 한마디 (불편했던 점·버그·바라는 점) | 긴 글(300자) | 자유 | 아니오 |
| name | 이름이나 별명 | 짧은 글(20자) | 자유 | 아니오 |

구글 설문지에서는 어떤 문항도 필수로 두지 않는다(빈 칸이 있으면 응답이 조용히 버려지기 때문). 필수 여부는 게임이 확인한다.

## 자동으로 붙는 기록(설문지 7~11번, 단답형)
| 키 | 설문지 문항 | 값 |
|---|---|---|
| reach | 최고 스테이지 | 열린 가장 높은 판 번호(unlockedMax) |
| runs | 판 수 | 지갑 runNo(출격할 때마다 +1 — 이미 있는 값) |
| mins | 플레이 시간(분) | 새 저장 칸 playSec(판이 끝날 때 run.time 을 더함) ÷ 60, 반올림 |
| device | 기기 | `휴대폰 · 아이폰 · 카카오톡` 꼴(기기 종류 · 운영체제 · 앱 안 여부) |
| etc | 기타 기록 | `깬 8 · 스토리 3 · r4.34 · #a1b2c3d4`(깬 판 수 · 본 스토리 수 · 게임 버전 · 익명 번호) |

익명 번호 = 처음 보낼 때 만든 무작위 8자(저장 칸 reviewAnon). 같은 기기의 여러 응답을 묶어 보는 용도다.
그 밖의 개인 정보(이메일·전화·위치·정확한 기기 모델)는 받지 않는다. 설문 창 아래에 무엇이 함께 가는지 보여 준다:
"게임 기록(최고 STAGE 9 · 12판)도 함께 보내요".

## 띄우는 때
- 결과 화면 오른쪽 위에 작은 보조 버튼 [리뷰 남기기]를 늘 둔다(id `review`, 기본 버튼·Enter 동작은 그대로).
- 판 수(runNo)가 3 이상인 결과 화면에서, 아직 초대를 안 했고 보낸 적도 없으면 초대 카드를 한 번 띄운다
  ("리뷰 1분만 부탁해요!" · [쓰기] [나중에]). 띄우는 순간 저장 칸 reviewAsked = true — [나중에]를 눌러도 다시 안 띄운다.
  보스 판 승리로 스토리 컷이 먼저 나오면, 컷이 끝나고 결과 화면이 될 때 띄운다.
- 창이 열린 뒤 0.6초 동안은 누르기를 받지 않는다(판 끝에 누르던 손가락으로 바로 닫히지 않게 — 스토리 0.5초 잠금과 같은 이유).
- 보낸 뒤에는 "고마워요! 잘 받았어요."를 보여 준다. [리뷰 남기기]는 남겨 두어 다시 보낼 수 있다(창 위에 "이미 N번 보내 주셨어요").

## 구성
- `rush3/review.js`(순수): 문항 표 REVIEW_QS · 설문지 주소와 칸 번호 REVIEW_FORM · 게임 버전 REVIEW_GAME_VER ·
  기록 만들기 reviewRecord · 기기 이름 deviceLabel · 보낼 값 buildReviewPairs · 필수 확인 reviewMissing · 초대 판정 shouldInvite · 익명 번호 makeAnon.
- `rush3/reviewui.js`(DOM): 설문 창(초대 카드 · 문항 · 보내기 · 결과 줄). 게임과 같은 어두운 색, 입력 글자 16px(아이폰 확대 방지),
  `user-select: text`(페이지 전체는 none). 셸이 주입받은 콜백(onSubmit · onClose)만 부른다.
- `rush3/main.js`: 상태 `'review'`(그림은 결과 화면 그대로, 버튼 없음) · 결과 화면 [리뷰 남기기] · 초대 · 전송과 재전송 ·
  창이 열린 동안 게임 키(Enter·Space·조향)와 캔버스 누르기를 무시(ESC = 창 닫기). 진입점 `boot(…, { story: true, review: true })`.
  `?dev=1`이면 꺼진다(점검 도구 그림이 바뀌지 않게) — 단 `?dev=1&review=1`은 켠다(확인용).
  검사는 deps.review · deps.reviewUi(가짜 창) · deps.fetch(가짜 전송) · deps.makeAnon 으로 주입한다.
- `rush3/save.js`: 새 칸 playSec(수, 기본 0) · reviewAnon(문자열) · reviewAsked(참/거짓) · reviewSent(수) · reviewPending(보낼 값 쌍 목록 | null).
  defaults·normalize 두 곳 모두에 둔다(한 곳만 있으면 patch 때 조용히 버려진다). 스키마 v 는 3 그대로.

## 전송
`fetch(REVIEW_FORM.action, { method: 'POST', mode: 'no-cors', body: new URLSearchParams(pairs) })`.
응답 내용은 읽을 수 없다(no-cors). 그래서 ① 보내기 전에 reviewPending 에 값을 적어 두고 ② fetch 가 끝나면(resolve) 성공으로 보고
reviewPending 을 비우고 reviewSent +1 ③ 실패(reject — 인터넷 끊김)면 "못 보냈어요. 다음에 게임을 열면 자동으로 다시 보내요" + [구글 설문지에서 직접 쓰기] 링크.
다음 실행 때 reviewPending 이 있으면 한 번 조용히 다시 보낸다.
값이 설문지 선택지와 다르면 구글이 조용히 버리므로, 출시 전 실제 전송 검사로 모든 칸이 들어가는지 확인한다.

## 구글 설문지(LaserMoon 계정)
제목 "스타포지 러시 친구 테스트 리뷰", 한 페이지(섹션 나누지 않음), 위 11문항 순서 그대로, 필수 없음,
이메일 수집 안 함 · 응답 1회 제한 끔(둘 다 로그인을 요구하게 된다), 게시 대상 = 링크가 있는 모든 사용자.
응답 탭에서 새 구글 시트에 연결. 칸 번호(entry.N)와 formResponse 주소는 공개 설문 페이지에서 읽어 REVIEW_FORM 에 적는다.

## 검사
- Node: review.js 순수 함수(문항 표가 설문지 값과 같음 · 보낼 값 · 필수 · 초대 · 기기 이름) · save 새 칸 정규화 ·
  셸 흐름(결과 버튼 · 3판 뒤 초대 1회 · 창이 열린 동안 Enter 가 출격하지 않음 · 전송 성공/실패/재전송).
- 브라우저: 로컬 서버 + Playwright(휴대폰 크기, 카카오톡 UA)로 창 모양 캡처, 어절 쪼개짐 없음 확인.
- 실제 전송: 별명 "[테스트]"로 2~3건 보내 설문지 응답·시트에 11칸이 다 들어오는지 확인. 응답 삭제는 하지 않는다
  (되돌릴 수 없는 일 — 이사님이 지우시거나, 요약할 때 "[테스트]"를 뺀다).

## 끄기
테스트가 끝나면 진입점의 `review: true` 한 줄을 지운다(버튼·초대·재전송 모두 꺼짐). 설문지는 응답 받기를 끄면 된다.
