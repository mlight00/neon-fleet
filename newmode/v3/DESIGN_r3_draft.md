## 1. 게이트 전용 사격 활성 구간(셔터) — 검수 Q1

### 1-1. 왜 전체 사거리를 건드리지 않는가

전투 전체의 탄 정리선(`z > run.z + 650`)을 줄이면 통·적·정예 사거리가 같이 줄어든다. 그래서 **게이트에만 적용되는 사격 가능 구간**을 만든다. 기본 규칙 **유효탄 1발 = +1 은 그대로 유지**하고, **병력 수에 비례한 숨은 감쇠는 넣지 않는다.**

### 1-2. 규칙

게이트 행에 `armZ`(부대 중심 기준 전방 거리, px)를 둔다.

```js
row = { id, z, h, cells, passed, bypass, armZ, armed }
```

- `armZ`: `number | null`. `null` = 항상 열림(학습용 게이트). 출발값 **340**, 실험 범위 300~380.
- `armed`: 판 시작 시 `armZ === null ? true : false`. 매 STEP `row.z - run.z <= row.armZ` 가 처음 성립하는 STEP 에 `true` 로 바뀌고, 그 뒤로는 되돌아가지 않는다(`run.z` 는 감소하지 않는다 — 보스전 중에는 멈출 뿐이다).
- **닫힌 셔터(`armed === false`)에 닿은 탄은 흡수한다. 값은 변하지 않는다.**

### 1-3. 흡수인가 통과인가 — 흡수로 확정

| 근거 | 내용 |
|---|---|
| 규칙이 보여야 한다 | 화면에 닫힌 셔터 판을 그려 놓고 탄이 통과하면 "왜 안 오르지"의 답이 화면에 없다. 흡수는 탄이 판에 부딪히는 것을 그대로 보여준다. |
| 기존 계약과 같은 말 | 벽·미개봉 통·미통과 게이트는 이미 전부 "탄을 흡수한다". 셔터만 예외를 두면 충돌 규칙이 두 갈래가 된다. |
| 손실이 거의 없다 | 셔터가 가장 가까운 후보일 때만 흡수가 일어난다. 즉 부대와 셔터 사이에 아무것도 없을 때뿐이고, 그때 흡수되는 탄은 원래 정리선까지 날아가 사라질 탄이다. |
| 부작용은 좁고 관측 가능 | 셔터보다 **더 먼** 적(전방 340~662px 구간)이 잠깐 가려진다. 적은 부대 쪽으로 오므로 곧 셔터 앞으로 나오며, 이 구간은 10장 `V3-GATE-ARM` 검사 대상이다. |

### 1-4. STEP 처리 순서에 넣는 위치

계약서 4장 순서에 **3-b 단계**를 새로 넣는다(스폰 다음, 사격 앞). 그 STEP의 탄 충돌(5단계)이 올바른 셔터 상태를 보게 하려면 `run.z` 갱신(2단계) 뒤여야 한다.

```
1 조향 → 2 전진 → 3 스폰 → [3-b 게이트 셔터 갱신] → 4 사격 → 5 아군 탄 → … → 11 승패
```

`gates.js` 에 순수 함수를 추가한다.

```js
// 열리는 STEP 에 이벤트 gateArm 을 정확히 1회 낸다
export function updateGateArm(row, run, events) {
  if (row.armed || row.passed) return false;
  if (row.armZ != null && row.z - run.z > row.armZ) return false;
  row.armed = true;
  events.push({ type: 'gateArm', id: row.id, z: row.z, x: (row.cells[0].x0 + row.cells[row.cells.length - 1].x1) / 2 });
  return true;
}
```

### 1-5. `hitGateCell` 계약 변경

셔터 상태는 **행**이 갖고 칸은 갖지 않는다(단일 진실). 그래서 시그니처에 `row` 를 추가한다.

```js
// 변경 전: hitGateCell(cell, bullet, events)
// 변경 후:
export function hitGateCell(row, cell, bullet, events) {
  bullet.dead = true;                     // 흡수는 어느 경우든 일어난다
  if (!row.armed) { events.push({ type: 'gateBlock', id: row.id, idx: cell.idx, x: bullet.x, z: row.z }); return true; }
  // 이하 기존과 동일: value = min(maxValue, value + gateHit), flashT, gateFlip/gateHit
}
```

- 호출부는 `combat.js` 의 `moveBullets` 안 `else if (kind === 2) hitGateCell(cell, b, ev);` 한 곳뿐 → `hitGateCell(obj, cell, b, ev)` 로 바꾼다(`obj` 에 이미 행이 들어 있다).
- 기존 `tests/rush3-gates.test.mjs` 의 `hitGateCell` 호출은 전부 인자 1개가 늘어난다. **기존 검사의 기대값은 바꾸지 않는다**(행을 `armed: true` 로 만들어 넘긴다).
- `makeGateRow(def)` 는 `armZ: def.armZ === undefined ? BAL3.gate.armZ : def.armZ`, `armed: (그 값 == null)` 로 초기화한다. `balance.js` 에 `gate.armZ: 340` 을 추가한다.

> **⚠ 넣을 곳을 틀리면 흡수가 아니라 통과가 된다.**
> F4 수정으로 `gates.js` 에 `sweepContactGate(row, cell, bullet)`(최초 교차 z 또는 `null`)이 생겼고 `combat.js` 의 후보 등록이 그 함수를 쓴다.

### 2-2. 스폰 열·간격·통로 폭 규격 — **r3.1 재작성(지적 5)**

**r3 의 오류.** r3 은 "인접 잡졸 x 간격 ≥ 70(부대 반폭 상한 60 + 여유 10)"이라고 썼다. 이것은 두 가지가 틀렸다.

1. 부대가 지나가려면 필요한 것은 **중심 간 간격**이 아니라 **가장자리 사이 폭**이고, 그 폭은 `2 × 부대 반폭` 이상이어야 한다. 중심 간 간격으로 쓰면 `2 × 반폭 + 2 × 적 반지름`이 된다.
2. 부대 반폭은 상한 60 이 아니라 **그 구간의 실제 병력에 따른 `formationHalfWidth(n)`** 이다. 벽 밖에서는 압축이 없으므로 `hwMax 60` 은 걸리지 않는다(대형은 60 을 훌쩍 넘는다).

**r3.1 규격**

```
가장자리 간격 = |x(i+1) − x(i)| − 2 × 적 반지름          (도로 가장자리와의 간격 = 도로 끝 − (x ± r))
필요 폭       = 2 × formationHalfWidth(그 구간 예상 병력) + 10
통로 성립     ⟺ 가장자리 간격 ≥ 필요 폭
```

### 3-2. 두 안 비교

| 안 | 내용 | 양쪽 동시 획득 차단 | 선택 전 정보 | 새 규칙 |
|---|---|---|---|---|
| **A. 통을 z2500~2600 으로 이동** | 통 z 를 `wall.z0 − 60 + 662` 보다 뒤로 | **가능**(2402 이상이면 성립) | **불가능** | 없음 |
| **B. 통로 진입 후 열리는 차폐** | 통에 `coverZ` 를 두고 그 전에는 탄 흡수 | 가능 | 가능 | 통 필드 1개 |

**A 안이 정보를 못 주는 이유(산수).** 화면 진입은 `obj.z − run.z <= 760`. 그러니 통이 보이기 시작하는 시점은 `run.z = 통.z − 760`.
선택(확정) 전에 통을 보려면 `통.z − 760 < 1740` → `통.z < 2500`.
확정 전에 못 쏘게 하려면 `통.z > 1740 + 662 = 2402`.
**두 조건이 겹치는 구간은 2402 < z < 2500, 폭 98px = 0.52초뿐이다.** 즉 A 안을 안전하게 잡으면(z2500~2600) **통은 통로가 확정된 뒤에야 화면에 나타난다 = 눈 감고 고르는 선택**이 된다.

### 3-3. 채택: B(차폐) + 통로 안내 표지

**규칙**

```js
supply = { …기존…, coverZ: null | number, pairId: null | string, skipped: false }
```

- `coverZ != null && run.z < s.coverZ` 이면 **탄을 흡수하고 내구는 줄지 않는다**. 이벤트 `supplyBlock`.
- **코드의 `hitSupply` 는 이미 `hitSupply(s, bullet, events, run)` 4인자다**(`rush3/supply.js:80`, 호출부 `combat.js:178`). 따라서 **코드 시그니처는 바뀌지 않고** 함수 첫머리에 검사 1줄만 넣는다. 다만 **계약서 2장·3-3장은 아직 3인자(`hitSupply(s, bullet, events)`)로 적혀 있어 계약서 쪽 정정이 필요하다**(지적 5 · §12).
- `supplyActive(s)` 는 차폐를 보지 않는다(차폐된 통도 충돌 후보로 남아 탄을 흡수한다 — 1-3 과 같은 이유). `skipped` 취급은 6-1 참조.

**`coverZ` 값은 확정선이 아니라 '비행시간 보정선'이다 — r3.2 정정(지적 1)**

r3.1 은 `coverZ = wall.z0 − 60`(통로 확정 z)으로 잡았다. **그것으로는 배제가 닫히지 않는다.** 확정 **전에** 발사돼 아직 날아가는 중인 탄이, 차폐가 열린 뒤에 반대편 통에 도착하기 때문이다.

```
coverZ = ceil( commitZ + (s.z − commitZ) × scroll / vzMin )      commitZ = wall.z0 − 60
scroll = 190 (balance.js)   ·   vzMin = 650 (weapons.heavy.vz = 가장 느린 탄)
```

유도: `run.z = Z0` 에서 쏜 탄이 통 `s.z` 에 닿는 시각의 `run.z` 는 `Z0 + (s.z − Z0) × scroll / vz` 다. 확정 직전(`Z0 = commitZ`)에 쏜 **가장 느린** 탄이 도착하는 그 지점까지 차폐를 유지하면, **확정 전에 발사된 탄은 하나도 반대편 통에 닿지 못한다.**

| 지점 | `commitZ` | 통 z | r3.1 `coverZ` | **r3.2 `coverZ`** | 남는 사격창 |
|---|---:|---:|---:|---:|---:|
| S2 `w1` | 1740 | 2300 | 1740 | **1904** | 396px |
| S3 `wA`(p1) | 2340 | 2800 | 2340 | **2475** | 325px |
| S3 `wB`(p2) | 3090 | **3500**(4-3 에서 3400 → 3500) | 3090 | **3210** | 290px |
| S3 `wD` | 5940 | 6300 | 5940 | **6046** | 254px |

**실측 확인**(게임 코드 무수정). 정책 = "확정선 직전 T 까지 한쪽에 붙어 사격 → T 에서 반대편으로 대시", T 는 확정선 −400 부터 확정선까지 훑는다.


- 벽 앞머리(`z0`)에 좌/우 통로 내용물을 아이콘+숫자로 그린다(병사 실루엣 ×3 / 기관총 아이콘 / `none` = 빈 통로).

### 4-2. 설계 원칙 — **r3.1 전면 교체(지적 1)**

**r3 의 오류.** r3 은 "탄은 위로만 나가므로 **같은 z 에 좌·우 물체를 놓으면** 한 STEP 에 한쪽만 깎을 수 있다. 이것이 유일하고 정직한 배제 장치"라고 썼다. **틀렸다.** 한 STEP 에 한쪽만 깎는 것은 맞지만, 판은 STEP 이 아니라 **사거리 662px = 3.48초** 동안 이어지고 좌↔우 이동은 **180px = 0.72초**뿐이다. 그래서 부대는 **같은 z 의 좌·우를 차례로 다 먹는다.**

즉 r3 의 선택 A(연속증원 vs 병사 5)·선택 B(무기 선택이 다음 게이트를 바꾼다)는 **성립하지 않았다.**

**r3.2 원칙**(1·2 는 r3.2 에서 고쳤다)

1. **배제는 벽으로만 보장된다.** 탄 x 는 부대 중심 ± 대형 반폭 안이고, 통로에 갇힌 부대의 x 는 벽을 넘지 못한다. 그래서 **통로 확정 뒤에 새로 쏘는 탄은 반대편 통을 어떤 병력·어떤 무기로도 못 깬다.** 이것이 병력 규모와 무관하게 성립하는 **유일한** 장치다. — **단, 확정 전에 발사돼 아직 비행 중인 탄은 벽이 막지 못한다.** 그래서 원칙 2가 반드시 함께 있어야 한다(r3.2 정정, 지적 1).
2. **차폐(`coverZ`)는 확정선이 아니라 비행시간을 더한 선에서 열린다.** 벽만 두면 확정 **전에** 사거리로 양쪽을 다 먹고(3-1 재현), `coverZ` 를 확정선(`wall.z0 − 60`)에 두면 **확정 직전에 쏜 탄이 차폐가 걷힌 뒤 도착해** 여전히 양쪽을 먹는다(§3-3 실측). 그래서 `coverZ = ceil(commitZ + (s.z − commitZ) × scroll / vzMin)` 로 잡는다. **벽 없는 `coverZ`, `coverZ` 없는 벽, 확정선에 둔 `coverZ` 는 셋 다 배제가 아니다.**
3. **사격창 경쟁(`armZ`·`coverZ` 겹치기)은 배제가 아니라 저울이다.** "통을 열면 게이트를 못 채운다"는 **병력 상한 안에서만** 성립한다. 상한을 넘는 대군은 둘 다 가져간다. 그 상한을 **실측해서 문서에 적는다**(4-4 선택 C).
4. **큰 보상은 남긴다.** 게이트 +40, 연속증원 발판 15는 그대로 둔다.
5. **위협도 좌우로 나눈다.** 한쪽에 서면 안전까지 독점하지 못하게 한다.
6. **적 HP 상향·병력 비례 숨은 감쇠는 쓰지 않는다.**

**선택 A(z2800, 벽 `wA` + `coverZ 2475`)** — 좌 연속증원은 개봉 뒤에도 유효탄 1발 = 발판 +1 이라 **최대 15명**까지 자란다. 대신 발판이 `z2860~3420`, `x150` 에 깔리므로 **좌측 차선에 묶인다**. 우 병사 통은 **즉시 확정 5명**이고 자유롭다.

**선택 B(z3500, 벽 `wB` + `coverZ 3210`)** — 무기를 **게이트 앞**에 둔 것이 핵심이다. 기관총은 게이트 유효탄이 소총의 약 2배(1-7: 9.3 vs 4.85/1인)라서 **`−25 → +40` 에 필요한 병력이 13.4명 → 7.0명으로 준다**. 중화기는 게이트 효율이 가장 낮은 대신(4.15/1인) 적 처리·정예전을 맡는다.

### 4-5. 고정 vs 계획 이동 기대치 — **`plan` 정책 정의 포함**

**`plan`(계획 이동) 정책 정의.** r3 은 `aim`(가장 가까운 미획득 대상을 쫓는 탐욕 봇)을 "계획 이동"처럼 다뤘다. 탐욕 봇은 **가장 가까운 것만** 보므로 "지금 이걸 버리고 저걸 얻는다"를 못 한다. 검수 Q4 가 요구한 것은 계획한 이동이므로, **설계가 의도한 경로를 그대로 따르는 결정적 스크립트 정책**을 따로 둔다(구간별 목표 x 표, 무작위 없음).

```js
// tests/rush3-sim.test.mjs 의 정책 표 (S3) — r3.2 수정(지적 2): 3900 통을 먹고 우 칸으로 간다
plan = [ [0,1100,160], [1100,1500,320], [1500,1900,160], [1900,3550,150],
         [3550,3760,150],            // 3900 통(coverZ 3660)을 좌에서 깬다 — 기관총 25명 기준 z3721 개봉
         [3760,4000,320],            // 그 뒤 우 칸(−25)으로 옮겨 상한 +40 까지 채운다
         [4000,5940,150], [5940,6400,150], [6400,Infinity,240] ]
```

**전환 z 3760 의 근거**(`review/verify/r31-plan-switch.mjs` · 고정 z 스크립트로 재현). 통 개봉 z 는 기관총 25명 **3721**, 29명 **3714** 이므로 3760 은 개봉 뒤다. 3760 에서 우 칸으로 옮기면 **기관총 25명 유효탄 104발 · 29명 114발**(필요 65발) → **우 칸 +40**. 전환을 3850 까지 늦추면 25명 유효탄 52발 → +27 로 떨어진다. 즉 3760 은 **여유 있게 잡은 값**이지 최적값이 아니다.

아래는 **이 배치가 주어졌을 때의 산수 예측**이다(4-1 처럼 실측이 아니다). 적 손실은 반영하지 않았다.

| 정책 | 경로 | 최고 병력(가설) | 무기 | 화력 지수 |
|---|---|---:|---|---:|
| right 고정 | 1500(+2) → `wA` 우(+5) → `wB` 우 heavy → 4000 우(10명 × 4.15 = 41 → **+16**) → `wD` 우 없음 | **≈ 26** | 중화기 | 26 × 5 = **130** |
| left 고정 | 1100(+2) → 1900(+3) → `wA` 좌 발판 15 → `wB` 좌 auto → 3900(+4) → 4000 좌(+12) → `wD` 좌(+10) | **≈ 49** | 기관총 | 49 × 4 = **196** |
| **plan** | 1100·1500·1900 전부 → `wA` 좌 발판 15 → `wB` 좌 auto → 3900 **획득 +4** → 4000 우 **+40** → `wD` 좌 +10 | **≈ 79** | 기관총 | 79 × 4 = **316** |

**화력 지수 = 생존 병력 × 무기 초당 dmg**(소총 2 · 기관총 4 · 중화기 5).

계획 이동이 left 대비 최고 병력 **+61%**·화력 **+61%**, right 대비 **+204%**·**+143%**. 검수 Q4 의 출발 가설(**25% 우위**)을 넉넉히 넘긴다. 넘치면 줄이고 모자라면 늘리되, 조정은 **배치(z·x·내구·상한)** 로만 하고 적 HP·숨은 감쇠로는 하지 않는다.

**얻는 통 개수(설계 예측)**: left **6개**(1100·1900·p1좌·p2좌·3900·6300) · right **3개**(1500·p1우·p2우) · plan **7개**(1100·1500·1900·p1좌·p2좌·3900·6300 — r3.2 에서 3900 이 추가됐다). → 10장 `POL-7` 은 이 예측과 어긋나지 않게 다시 썼다.

**구조적으로 배타적인 경로 변경 = 3회**(A·B·D, 벽 기반) **+ 사격창 저울 1회**(C) — 검수가 요구한 2회를 넘긴다.

```js
run    = { …, missedSupplies: 0, skippedSupplies: 0 }
```

**r3 의 오류.** r3 은 `skipped` 를 "같은 `pairId` 인 다른 통이 `opened`"로만 정의했다. 그러면
① 선택 D(z6300)처럼 **짝이 아예 없는** 통(우 통로 = 빈 통로)은 벽 반대편이라 못 얻는데도 `missed` 로 세고,
② S2 에서 우 통로를 고르고 우 통을 못 깨면 좌·우 **둘 다 `missed`**(2개)로 세는데 좌 통은 애초에 얻을 수 없었다.
검수 후속개선이 요구한 "획득 불가능해진 대안과 실제 기회 손실의 구분"이 안 된다.

**r3.1 기준: 지나는 시점에 '구조적으로 획득 불가능했는가'**

```
structurallyLost(s, run) =
  (a) 벽 배제 : 어떤 벽 w 에 대해  (w.z0 − 60) <= s.z <= w.z1  이고  run.wallSide[w.id] 가 정해져 있으며
                통 원이 그 통로 구간과 전혀 겹치지 않는다
                (side 'L' → s.x − s.r > w.x0 ,  side 'R' → s.x + s.r < w.x1)
  (b) 차폐 미개방 : s.coverZ != null && run.z < s.coverZ            (지나는 STEP 기준)
  (c) 쌍 배제 : s.pairId != null 이고 같은 pairId 의 다른 통 중 하나가 opened
```

- (a)·(b) 는 `run.walls`·`run.wallSide` 로 판정한다. **`passSupply` 시그니처는 그대로**다(`run` 안에 둘 다 있다).
- (b) 는 현재 배치(`coverZ` 가 언제나 통 z 보다 앞 — §3-3 표에서 254~396px 앞)에서는 발생하지 않는다. 앞으로 통로별 차폐를 쓸 때를 위한 **완결 조항**으로 남긴다.
- (a) 가 성립하려면 통이 **벽 끝보다 최소 1 STEP 앞**에 있어야 한다(3-3 ⚠ 상자).

**`passSupply(s, run, events)` 판정 순서 — 기존 조기 반환·z 창을 그대로 앞에 둔다**

```
0.   s.missed || s.skipped || (s.opened && s.kind !== 'chain')      → return false      ← 기존 + skipped 추가
0-b. !(run.prevZ < s.z && s.z <= run.z)                             → return false      ← 기존 z 창(그대로)
1.   s.opened (chain)                    → locked 처리만(기존과 동일)
2.   미개봉 + structurallyLost(s, run)   → s.skipped = true, run.skippedSupplies++, 이벤트 supplySkipped
                                           + chain 이면 s.locked = true               ← r3.2 추가(지적 3)
3.   그 외 미개봉                        → s.missed  = true, run.missedSupplies++,  이벤트 supplyMissed
                                           + chain 이면 s.locked = true               ← r3.2 추가(지적 3)
```

> **⚠ 2·3 분기에서 `locked` 를 빠뜨리면 기존 검사가 깨진다(r3.2, 지적 3).** 현행 `rush3/supply.js:107` `passSupply` 는 미개봉/개봉과 무관하게 마지막에 `if (s.kind === 'chain' && !s.locked) s.locked = true;` 를 돈다. r3.1 은 `locked` 를 1번 분기에만 달아 놓아, 그대로 옮기면 **`tests/rush3-supply.test.mjs:329` `V3-CHAIN: 미개봉 chain 을 지나면 missed + locked, 보상 없음`** 이 실패한다(현재 129개 중 통과 상태). S3 선택 A 의 좌 통이 바로 chain 이므로 **2번(skipped) 분기에서도 실제로 발생한다.** 구현할 때는 세 분기 뒤에 공통으로 한 줄을 두는 편이 안전하다 — 기존 코드 모양 그대로다.

> **⚠ r3 문장대로 옮기면 통을 지나기 전에 `skipped` 가 켜진다.** r3 은 판정을 1·2·3 세 줄로만 적어 `z` 창을 뺐다. 그러면 파트너가 열리는 STEP(예: p1 좌를 `run.z 2400` 에 개봉)에 곧바로 우 통이 `skipped` 로 집계된다 — **아직 깰 수 있는 통이 "지나쳤다"로 처리된다.** `0-b` 를 반드시 먼저 둔다.

- `supplyActive(s)` 에 **`skipped` 를 `missed` 와 같이 제외 조건으로 넣는다**(`!((s.opened && kind!=='chain') || s.missed || s.locked || s.skipped)`). `skipped` 는 지나는 STEP 에만 켜지므로 실제 동작은 바뀌지 않지만, "지나간 통은 충돌 후보가 아니다"를 한 규칙으로 유지한다.
- 화면 표현: `skipped` 통은 "밀려나며 사라지는" 연출 대신 **흐려지며 뒤로 빠지는** 연출로 구분한다(실수가 아니라는 신호).
- `pairId` 가 붙는 통: S2 `c1·c2`(`'w1'`), S3 `p1`(연속증원·병사 통), `p2`(기관총·중화기). **한 판에서 같은 `pairId` 는 최대 1개만 열릴 수 있다** — 이제 그 근거는 "같은 z" 가 아니라 **벽 + `coverZ`**(4-2)이고, `V3-SUPPLY-PAIR` 의 `PAIR-4` 가 `stepRun` 으로 검사한다.

### 6-2. 결과 화면 — 제안 한 줄 우선

`missedLine(run)` 위에 **실행 가능한 제안 한 줄(`adviceLine`)** 을 놓고, 제안이 있으면 그것을 크게, 놓친 것 요약은 작게 보여준다.

**`adviceLine` 은 신규 순수 모듈 `rush3/advice.js` 에 둔다(지적 6).**

```js
// rush3/advice.js — 결과 문구 선택. 순수 함수(난수·화면·balance·시계 없음)
export function adviceLine(run, stage) { … }
```

- `main.js` 에 두면 `V3-HINT` 검사가 셸을 import 해야 한다. `stages.js` 에 두면 배치 데이터 모듈이 `run` 상태를 읽게 된다. 그래서 **별도 모듈**이 맞다.
- `advice.js` 도 규칙 모듈과 같은 순수 제약을 받는다(`V3-PURE` 대상에 추가).

**힌트 데이터는 스테이지에 넣는다**(문구가 배치와 함께 관리되게).

```js
// stages.js DEFS 안
supplies: [ { …, hint: '분리벽 오른쪽 기관총을 확보하면 다음 무리를 빨리 정리할 수 있어요' } ]
gates:    [ { …, hint: '왼쪽 칸은 조금만 쏴도 확실합니다. 오른쪽은 병력이 더 모인 뒤에 노려 보세요' } ]
```

**선택 규칙(결정적 · 무작위 없음)**

| 순위 | 조건 | 문구 |
|---:|---|---|
| 1 | `lossByGate > 0` | 마지막으로 통과한 음수 게이트 행의 `hint` |
| 2 | `missedSupplies > 0` | 놓친(=`missed`) 통 중 **z 가 가장 작은** 통의 `hint` |
| 3 | `lossByShot >= lossByTouch && lossByShot > 0` | 기본 문구: "저격수는 예고선이 보일 때 옆으로 한 번만 비키면 됩니다" |
| 4 | `lossByTouch > 0` | 기본 문구: "돌격체는 쏘는 것보다 비키는 게 빠릅니다" |
| 5 | 그 외 | 성공 시 "다음엔 반대쪽 보급을 골라 보세요", 실패 시 기존 `missedLine` |

`skipped` 통은 **1~5 어느 순위에도 들어가지 않는다**(의도된 선택이므로).

## 7. 코스 버전

- **버그 수정 팩이 이미 그릇을 만들어 두었다.** `stages.js` 의 `DEFS[id]` 에 `version` 필드가 생겼고 `stageVersion(id)` 이 export 되며 `buildStage` 가 `d.version ?? 1` 을 쓴다. r3.1 이 할 일은 **`DEFS[1|2|3].version` 을 `1 → 2` 로 올리는 것뿐**이다.
- S1 은 배치를 바꾸지 않지만 **잡졸 `track 0`(2장)·게이트 셔터(1장)·z5300 `xs` 재지정(2-2)으로 진행 결과가 달라지므로 S1 도 `version: 2` 로 올린다.**
- **저장 구조는 이미 완성되어 있다**(수정 팩 담당이 계약서 7장과 함께 넣었다). r3.1 은 그 위에 얹기만 한다.

| 이미 있는 것 | 내용 |
|---|---|
| 저장 형태 | `stages[id].versions[stageVersion] = { cleared, attempts, bestSurvivors, bestTime }` |
| 단일 출처 | `DEFS[id].version` → `buildStage(id).version` · `stageVersion(id)` · `run.stageVersion` |
| 마이그레이션 | 구 저장(스테이지 칸에 기록이 바로 있던 형식)은 **지우지 않고 버전 1 로 귀속** |
| API | `getStage(id, version)` · `updateStage(id, patch, version)` · `getStageVersions(id)` |
| 화면 규칙 | 신기록 비교·attempts 증가는 **같은 버전 안에서만**. 스테이지 선택은 현재 버전 기록을 보여준다 |

- "이전 코스 기록도 한 줄 보여주기"는 지금 계약(옛 버전 기록은 저장에만 남고 화면에는 안 나온다)과 어긋나므로 **r3.1 범위에 넣지 않는다.** 필요하면 별건으로 올린다.

## 13. 남은 불확실성

1. **4-5 의 병력 예측은 산수다.** 적 손실·이동 지연·부대 폭에 따른 사선 이탈을 반영하지 않았다. 실제 24판 시뮬에서 25% 우위가 안 나오면 배치를 조정해야 한다.
2. **`armZ` 340 은 출발값이다.** 300~380 실측표(1-7)를 근거로 잡았을 뿐, 재미 기준으로 검증된 값이 아니다.
3. **잡졸 `track 0` 의 파급이 넓다.** 2-3 에서 S1 무조작 완주가 유지됨을 에뮬레이션으로 확인했지만(여유 2.2px → 새 xs 로 22.4px), S2·S3 의 손실 구조는 아직 재지 않았다.
4. **선택 C 의 저울은 병력 상한 안에서만 성립한다**(4-4). 상한 위 대군은 통과 +40 을 둘 다 가져간다. 21판 재실행에서 실제로 그 병력이 그 지점에 도달하는지 확인해야 한다.
5. **S3 에 벽이 3개가 된다.** 화면에서 벽이 반복 요소로 지루해 보이지 않는지, 표지 3쌍이 각각 다르게 읽히는지는 실기 확인이 필요하다. (배제를 벽으로만 만들 수 있다는 4-2 의 결론에서 나온 비용이다.)
6. **통로 안내 표지는 새 화면 요소**다. 480px 폭에서 좌·우 두 칸의 아이콘이 읽히는지 실기 확인이 필요하다.
7. **`hitGateCell` 시그니처 변경**은 기존 테스트 호출부를 건드린다. 기대값을 바꾸지 않도록 주의해야 한다. 그리고 1-5 의 ⚠ 상자대로 **셔터·차폐 검사를 교차 함수에 넣으면 흡수가 통과로 뒤집힌다.**
8. **작업 폴더를 다른 담당이 동시에 고치고 있다.** 초안 작성 중 `rush3/{combat,gates,input,main,save,stages,supply}.js`·계약서·테스트가 바뀌었고 검사 개수가 117 → 129 로 늘었다. 구현 착수 전에 **작업 폴더 상태와 검사 개수를 다시 확인**하고, 같은 파일을 동시에 고치지 않도록 순서를 조율해야 한다.
9. **`review/probe-local.mjs` 는 이 초안 작성자의 파일이 아니다.** 재실행하면 `probe-results-local-<tag>.json` 을 덮어쓴다. 비교용으로 돌릴 때는 태그를 따로 준다.
10. **9-4 의 새 측정은 전부 에뮬레이션이다.** `armZ`·`coverZ`·`track 0` 이 코드에 들어간 뒤 같은 값이 나오는지 다시 재야 한다.
11. **자동 검사 통과 ≠ 재미 검증.** 이 문서의 합격선을 다 넘겨도 초보 10~12명 플레이테스트는 별도로 해야 한다(검수 Q4).
12. **`coverZ` 공식은 `vzMin` 에 매달려 있다(r3.2).** 지금 가장 느린 탄은 중화기 650 이다. **650 보다 느린 무기·투사체를 추가하면 네 지점의 `coverZ` 가 전부 부족해져 배제가 다시 열린다.** `PAIR-4c` 가 그때 먼저 실패하도록 검사를 걸어 두지만, 그 상황이 오면 §3-3 의 대안(탄에 발사 시점 `z0` 를 실어 `hitSupply` 에서 흡수)으로 갈아타는 것이 더 안전하다.
13. **차폐 개방선이 확정선과 갈라졌다(r3.2).** 통로에 들어간 뒤 **0.5~0.9초 동안은 앞의 통을 못 깬다.** 규칙으로는 옳지만 화면에서 "왜 안 깨지지"로 읽힐 수 있다. 확정선과 개방선을 다른 색 2줄로 그리고 흡수 튐(`supplyBlock`)을 보여주기로 했으나(§3-3), **실기에서 읽히는지는 확인하지 못했다.**
14. **p2 통을 z3400 → 3500 으로 옮긴 것의 파급을 다 재지 않았다(r3.2).** 벽 `wB` 구간(3150~3550) 안이고 `wall.z1 − 4 = 3546` 조건도 지키지만, 통이 벽 끝에 100px 더 가까워졌으므로 **6-1 (a) 판정과 `wB` 통과 직후의 `skipped` 집계를 구현 후 다시 확인**해야 한다.
15. **§4-5 의 plan 예측이 다시 산수로 돌아갔다(r3.2).** 3900 통을 먹는 경로로 고치면서 최고 병력 예측이 75 → 79 로 올랐지만, 이 값도 적 손실·이동 지연을 반영하지 않은 산수다. 24판 실행에서 `POL-5`(1.25배)·`POL-8`(plan ≥ aim)을 실제로 넘는지가 판정 기준이다.
