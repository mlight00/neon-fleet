# 랜덤 길(로또) 구현 보고 — S3 빈 길 → 랜덤 길

작성 2026-09-17 · 대상 = 스타포지 러시 v3 1단계 S3 「군단」 · 계약서 개정 **r3.4**
근거 = **이사 지시(2026-09-16)**: "3스테이지에 빈 길은 무의미하다. 당연히 그 길로 안 간다. 빈 길이 아니라 랜덤 길을 만들어서 진입 시마다 로또처럼 좋거나 꽝인 선택이 랜덤으로 나오게 해 주자."

> ⚠️**이 보고서의 §1~8 은 1차 작성(수정 라운드 0) 시점의 기록이다.** 현행 기준은 **§9(라운드 1)·§10(라운드 2)** 이다 — 풀 ⑤ 는 `rusher4`(돌격체 4)가 아니라 **`trapGate`(−10 확정 게이트)** 이고, 차폐 개방선은 6046 이 아니라 **6094** 이다. §2·§4 의 수치를 읽기 전에 §10 을 먼저 보시기 바란다.

## 1. 무엇이 바뀌었나

**바뀐 곳은 S3 분리벽 `w3`(z 6000~7200)의 우측 통로 한 곳뿐이다.** S1·S2, S3 의 다른 선택(A·B·C), 난이도 표(보통/어려움/극한), 게이트·보급·무기·병사 hp 는 한 줄도 건드리지 않았다.

| | 이전(r3) | 이후(r3.4) |
|---|---|---|
| 좌 통로 | 병사 통 10명 + 저격수 2기 | **그대로** |
| 우 통로 | **빈 통로(보상 0)** | **랜덤 길** — 판마다 5종 중 1개를 균등 추첨 |
| 벽 표지 | 좌 "병사 10" / 우 "없음" | 좌 "병사 10" / 우 **"? 랜덤"** |
| 선택의 성격 | 아는 보상 vs 아무것도 없음 → **고르지 않는 것이 항상 옳다** | **아는 보상 vs 모르는 보상** |

문제의 핵심은 이사님 지적 그대로였다. 우측이 항상 0 이면 계산할 것이 없어 "선택"이 아니라 그냥 좌측 안내였다. 랜덤 길은 좌측의 **확정 병사 10명**과 우측의 **기대값(좋음 3 : 꽝 2)** 을 저울에 올린다. 배제 구조(벽 + 차폐 `coverZ`)는 그대로라 **한쪽만 얻는다**는 성질도 유지된다.

## 3. 시드 — 판마다 다르되, 규칙 난수는 여전히 0

```
셸(main.startRun)  lotterySeed = hashSeed('lot:' + stageId + ':' + attempts + ':' + dateNow())
규칙(stages.buildStage) → mulberry32(seed)() 를 한 번  → 균등 1/5
```

- **시계는 셸에만 있다**(`deps.dateNow` 로 주입 가능 — **수정 라운드 1에서 추가한 `V3-SHELL-LOTTERY` 가 이 조립을 고정한다**. 1차 작성 시점에는 이 검사가 없었다, §9 참조). 규칙 계층은 인자로 받은 정수 시드로 `mulberry32` 를 **한 번** 돌릴 뿐이라 **`stepRun` 안에 난수도 분기도 없다**(`V3-PURE` 유지, `LOT-8` 정적 검사).
- 시드를 생략하면 `LOTTERY_DEFAULT_SEED = hashSeed('rush3:lottery:default') = 4218602812` → 기본 추첨 결과 `badGate`. 검사·봇 시뮬 24판·27판이 전부 이 기준선을 쓴다(그래서 기존 193건이 무수정으로 통과했다).
- **재도전 버튼도 새 시드**다(`attempts` 와 시계가 모두 바뀐다). 이는 계약서 §0 '재도전 동일 배치' 원칙의 **명시적 예외**이며, 그 근거(이사 지시)를 §0·§3-9 두 곳에 적어 두었다.
- 추첨 결과는 `stage.lottery` → `run.lottery` 로 흐른다. **규칙은 이 필드를 읽지 않는다** — 셸의 결과 한 줄과 '?' 연출 전용이다.

## 8. 남은 판단거리(이사님 확인 사항)

출발값이라 **사람 플레이로 지점을 찾아야 하는 것**이 두 가지 있다. 지금 결정하실 필요는 없고, 실플레이 뒤 소감만 주시면 수치만 고쳐 넣는다.

1. **좋음 3 : 꽝 2 비율.** 기대값이 좌측(확정 병사 10)보다 유리한 쪽으로 기울어 있으면 "항상 오른쪽"이 되어 다시 선택이 아니게 된다. 반대로 꽝이 잦으면 "항상 왼쪽"이 된다. 봇으로는 알 수 없는 영역이다.
2. **꽝의 아픔 크기.** −15 게이트는 쏘면 0 까지 막을 수 있어 **병력이 많을수록 덜 아프고**, 돌격체 4 는 비키면 피해가 거의 없다. 지금은 둘 다 "손해가 작은 꽝"이라 로또의 긴장이 약할 수 있다.

## 10. 수정 라운드 2(2026-09-17) — 지적 2건 반영

지적 2건은 **둘 다 타당했고**, 둘 다 "검사가 지나가는 길만 봤다"는 같은 계열이었다. 하나는 **꽝이 꽝이 아니었던 것**, 하나는 **차폐 공식이 실제 탄 하나를 덜 센 것**이다. 계약서는 **r3.4(수정 라운드 2)** 로 같은 작업에서 갱신했다.

### 10-1. [major 1] 풀 ⑤ `rusher4`(돌격체 4)는 손실 0 — '꽝'이 아니었다

**무엇이 문제였나.** 지적대로다. 실측(`_probe_r2a.mjs`, 벽 `w3` 를 빠져나온 z 7200 시점):

### 10-2. [major 2] `coverZFor` 가 1 STEP 지연과 대형 깊이를 안 셌다

**무엇이 문제였나.** 지적대로다. 옛 공식은 `commitZ = wall.z0 − 60` 에서 **부대 중심**이 쏜 탄만 셌다. 실제로는 두 가지가 더 있다.

1. **1 STEP 지연** — `clampCenter` 는 `stepRun` 1단계에서 **직전 STEP 의 `run.z`** 로 통로를 판정한다. 그래서 아직 통로 제약을 받지 않은 대형이 쏘는 마지막 STEP 은 `commitZ + scroll × STEP`(+3.17px)이다.
2. **대형 깊이** — 탄은 `run.z − dy` 에서 출발한다. 뒷줄 유닛의 탄은 `dy` 만큼 더 날아가 **가장 늦게** 도착한다(유닛 상한 150 기준 `dy` 최대 = **159**).
