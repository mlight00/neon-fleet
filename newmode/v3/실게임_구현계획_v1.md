## 1. '실제 게임'의 1차 공개 범위

### 1-1. 최종 게임은 세 모드다 (01 §4)

| 모드 | 01 §4 원문 요지 | 지금 상태 |
|---|---|---|
| **A. 즉시 출격 — 순수 전투** | "별도 육성 없이 시작하는 30~60초짜리 스테이지… 일반 출격 버튼의 기본 목적지는 이 모드다" | 1단계 시제품이 이 모드다(3스테이지). 목표 24 |
| **B. 도시 탈환 — 캠페인** | "전투 → 지역 확보 → 영웅/자원/설계도 → 기지 성장 → 다음 전투" | 전부 미착수(V33~V52 예정). 목표 60 |
| **C. 특수 작전** | "캠페인 지도에서 발생하는 구출전과 아레나 보스전, 시간제 보상전을 모아 재도전" | 전부 미착수. B에 딸린 재도전 창구 |

### 1-2. 권고 — 1차 공개 = **모드 A 완성판**

**순수 전투 24스테이지 + 기록/공유 + 모바일.** 여기까지가 "남에게 보여줄 수 있는 최소판"이다. 캠페인·기지·영웅·드론(모드 B·C)은 2차 공개로 분리한다.

### 1-3. 그렇게 권고하는 근거 네 가지

1. **01 §13이 이미 그 순서로 적어 놓았다.** 2단계 = "순수 전투 완성 … 12개 스테이지를 먼저 완성한다. 이어서 24개까지 확장한다", 3단계 = "캠페인 성장 연결". 계획을 새로 발명하는 것이 아니라 확정된 순서를 지키는 것이다.
2. **모드 A만으로 게임이 성립한다.** 01 §4 A는 "일반 출격 버튼의 기본 목적지"이고 "영웅 육성 수치와 기지 생산 때문에 정답 경로가 바뀌지 않게 한다"고 못 박았다. 즉 **모드 A는 다른 모드에 의존하지 않도록 설계돼 있다.** 반대로 모드 B는 모드 A의 전투 위에 얹히므로 A 없이 B만 낼 수는 없다.
3. **검수자가 같은 말을 했다.** 검수2 §4 Q5: "대량 스테이지 제작과 새로운 육성 체계 확장은 초보가 지금의 규칙을 이해하는지 확인한 뒤가 효율적이다."
4. **남은 일의 크기가 다르다.** 모드 A를 24까지 채우는 데 필요한 새 장치는 7개(3칸 게이트·차폐물·움직이는 보급·구출 캡슐·보너스전·복수 정예·아레나)다. 모드 B는 그것에 더해 영웅 6명·편성·레벨/스킬·작전 지도·기지 10건물·자원 3종·훈련·병원·드론 — **화면과 저장 구조가 통째로 하나 더 생긴다.** 둘을 한 번에 공개하면 공개가 그만큼 뒤로 밀리고, 그동안 모드 A는 아무에게도 검증받지 못한 채 쌓인다.

### 1-4. 1차 공개에서 빠지는 것과, 빠져도 되는 이유

| 빠지는 것 | 02 요소 | 빠져도 되는 이유 |
|---|---|---|
| 영웅 6명·5인 편성·레벨/스킬·장비 | V33~V40 | 01 §4 A가 "순수 전투에는 육성이 유입되지 않는다"고 분리해 놓았다. 없어도 모드 A는 완결된다 |
| 기지·건물·자원·훈련·병원 | V44~V48 | 같은 이유. 기지는 "성공한 전투가 땅과 건물을 바꾸는" 장치(01 §7)라 전투가 먼저 완성돼야 의미가 생긴다 |
| 드론 | V50~V52 | 01 §6이 "드론 센터를 복구하면 해금"이라고 기지에 매달아 놓았다 |
| 이야기 대화·임무 보상 | V49 | 캠페인의 진행 장치 |
| 상점·채팅·동맹 | V53·V54 | 02 문서가 "구현 대상 아님 / 서버 확장 목록"으로 이미 분류 |

**단, 1차 공개에 반드시 들어가야 하는 것**(모드 A의 완결 조건): 구출 캡슐(V22)·아레나 보스(V27·V28)·보너스전(V43)은 **캠페인 소속이 아니라 전투 장치**다. 01 §4 C가 이 셋을 "특수 작전"으로 묶지만, 01 §13 2단계 완료 기준은 "02 문서의 **전투 요소**가 모두 실제 플레이에 등장"을 요구한다. 그래서 1차 공개에 포함한다. 다만 구출 캡슐의 보상만 "영구 영웅 해금" 대신 **그 판 안의 임시 동료 + 기록**으로 처리한다(영웅 시스템이 2차 공개이므로).

날짜를 약속하지 않는다. **순서·의존·완료 기준·검증 방법**만 적는다. 이유는 두 가지다 — ① 그림 제작이 이사님 일정에 달려 있고 ② 초보 관찰 3~5명 섭외가 사람 일정이라 우리가 통제할 수 없다.

### 묶음 A — 남은 정리 (지금 시작 가능)

검수2 §4 Q5의 1~3번(짧은 보완 → 정책 결정 → 스마트폰 실기와 초보 관찰)에 해당한다. 그중 1~2번(N1 안내·N2 셔터 표현·N4 결과 문구·시드 정책·확정 손실 표현)은 **이미 반영·커밋 완료**다(STATUS: 커밋 `e83b82a`·`a46a44d`·`1bd1620`, 검사 243). 그래서 A에 남은 것은 셋이다.

### 묶음 B — 2단계 순수 전투

## 3. 완료 기준과 검증 3층

### 3-1. 01 §13의 완료 기준 — 원문 인용

우리가 새로 만든 기준이 아니라 **기획서에 이미 적혀 있는 문장**이다. 바꾸지 않고 그대로 옮긴다.

> **1단계 — 기준 전투 3개**
> 완료 기준: 게이트에 쏘는 이유를 설명 없이 이해함 / 무기 획득 후 실제 처치 시간이 감소함 / 같은 스테이지에서 다른 경로를 시험할 수 있음 / 병력 증가가 그림·탄막에 즉시 드러남.

> **2단계 — 순수 전투 완성**
> 완료 기준: 02 문서의 전투 요소가 모두 실제 플레이에 등장하고, 모바일에서 벽·포인터 취소·아레나 전환까지 동작한다.

> **3단계 — 캠페인 성장 연결**
> 완료 기준: 전투 승리가 영구 결과를 남김 / 성장 후 같은 적을 상대했을 때 차이가 확인됨 / 기지를 이용하지 않고도 순수 모드 실행 가능 / 캠페인 재료 부족으로 진행 불능이 되지 않음.

> **4단계 — 결과·공유·마감**
> 영웅별 기여도, 실패 안내, 기록 복사, 일일 동일 코스, 저장 내보내기/가져오기, 소리·화면 조절을 마감한다. 실제 온라인 채팅·동맹을 만들려면 별도 서버 단계로 분리한다.

**주의 — 1단계 완료 기준은 아직 전부 충족되지 않았다.** 네 항목 중 앞의 셋은 이사님 실플레이로 확인됐지만(STATUS 1차 소감), **"설명 없이 이해함"은 만든 사람이 아닌 사람으로 확인해야** 성립한다. 검수2 §4 Q1의 지적이 바로 이것이다. 그래서 묶음 A-3(초보 관찰)이 **1단계를 닫는 일**이기도 하다.

### 3-2. 검증 3층 — 검수2 §4 Q3 권고를 그대로 쓴다

> "검사는 세 층으로 나누자: 규칙 회귀, 여러 조작 정책의 완주 가능성, 사람의 이해·재도전 의향."

| 층 | 무엇을 묻는가 | 도구 | 지금 상태 | 앞으로 |
|---|---|---|---|---|
| **1층 — 규칙 회귀** | "어제 되던 게 오늘도 되는가" | `node --test tests/rush3-*.test.mjs` | **243건 통과** | 새 장치마다 전용 검사를 함께 만든다. 장치 하나 = 검사 묶음 하나(`V3-` 접두) |
| **2층 — 조작 정책 완주 가능성** | "이길 수 있는 조작이 존재하는가" | 봇 8정책 × 스테이지 × 난이도(`tests/lib/rush3-policies.mjs`) | 성공 경로 봇 `planBoss` 추가 완료(r3.5). **지옥 S2만 미입증 — 기록으로 남김** | 새 스테이지마다 정책표를 낸다. **"실패하도록 짜인 봇을 통과시키는 것이 게임의 목표가 아니다"**(검수2 Q3) — 봇을 통과시키려고 전투를 약하게 만들지 않는다 |

## 4. 기술 계획 — 무엇을 확장하고 무엇을 새로 쓰는가

### 4-1. 그대로 쓰는 것(건드리지 않는다)

현재 rush3 구조의 핵심 성질은 **"규칙은 순수 함수, 화면·입력·루프는 규칙을 호출만 한다"**(계약서 §0)이다. 이 성질이 243건의 검사와 봇 시뮬을 가능하게 한다. **확장은 전부 이 경계를 지키는 방식으로 한다.**

- `combat.js`의 **고정 시간 간격(STEP = 1/60초)** — 30/60/120Hz에서 같은 결과.
- **규칙 모듈은 난수를 import하지 않는다**(정적 검사 `V3-PURE`). 랜덤 길은 `buildStage` 시점에 한 번만 뽑고 `stepRun` 안에는 난수가 없다.
- `gates.js`·`supply.js`·`squad.js`의 순수 함수 계약과 그 검사.
- `save.js`의 **기록 칸 = stageId + 코스 버전 + 난이도** 구조와 마이그레이션 규칙("실재하는 기록은 절대 지우지 않는다").

### 4-2. 확장하는 것 — `stages.js` 정의 형식

지금 스테이지는 `DEFS[id]` 한 덩어리에 `gates`·`supplies`·`walls`·`spawns`·`elite`가 들어 있는 **표 형식**이다. 새 장치 7개는 **이 표에 칸을 더하는 방식**으로 넣는다. 형식을 갈아엎지 않는 것이 핵심이다 — 형식을 바꾸면 기존 3스테이지의 검사가 전부 다시 쓰여야 한다.

| 새 장치 | 정의 형식 확장 | 규칙 모듈 변경 | 기존 검사 영향 |
|---|---|---|---|
| **3칸 게이트** | `gates[].cells`를 3개로 — **이미 배열이라 형식 변경이 없다.** 도로 80~400을 3등분(80~187·187~293·293~400) | `cellAt(row, x)`은 이미 임의 칸 수를 받는다. **"칸 합집합이 도로를 빈틈없이 덮는지" 검사만 3칸으로 확장** | 없음(추가만) |
| **차폐물** | `walls[]`에 `kind: 'cover'`(짧은 가림막, 통로를 막지 않고 사선만 막음) 추가 | 탄 충돌에 '흡수' 한 갈래 추가 — 벽·미개봉 통·닫힌 셔터가 이미 전부 흡수라 **같은 갈래에 얹힌다** | 없음 |
| **움직이는 보급** | `supplies[]`에 `move: { vx, x0, x1 }` 추가(좌우 왕복) | `hitSupply`의 x 판정이 고정 x를 읽던 것을 현재 x로. **z는 그대로 고정** | `supplyCovered`·`pairId` 규칙과 충돌 없음 |
| **구출 캡슐** | `supplies[]`에 `kind: 'rescue'`, `payload: { rescueId }` | 파괴 시 `rescued` 플래그 + 이벤트. **판의 승패 조건은 바꾸지 않는다**(놓쳐도 실패 아님) | 없음 |
| **보너스전** | `DEFS[id].bonus = { seconds, targets: [...] }` | **본전투 종료 후의 별도 phase.** `run.phase = 'road' | 'arena' | 'bonus' | 'done'` | phase 도입이 가장 큰 변경(4-3) |
| **복수 정예** | `elite`(단일 객체) → `elites`(배열). 기존 `elite`는 배열 1개로 자동 변환 | 보스 상태 `run.boss`(단일) → `run.bosses`(배열). **승리 조건 = 전원 격파** | 변환 계층으로 기존 검사 보존 |
| **아레나** | `DEFS[id].arena = { z, bossId, rect }` | `run.phase = 'arena'`에서 스크롤 0 + 상하 이동 허용 | phase 도입 |

**phase 도입이 이번 확장의 가장 큰 구조 변경이다.** 지금은 판 전체가 "앞으로 굴러가는 한 가지 상태"다. 여기에 아레나(스크롤 멈춤·상하 이동)와 보너스전(본전투 종료 후)이 들어오면 상태가 셋으로 늘어난다. **권고: `phase`를 `run`에 한 칸 추가하고, `stepRun`이 phase별 하위 함수를 부르는 구조로 나눈다.** 기존 세 스테이지는 `phase: 'road'`로 시작해 끝까지 `'road'`이므로 **동작이 한 줄도 바뀌지 않는다**(회귀 0).

### 4-4. 저장 스키마 v4

지금은 `starforgeRush.v3` = `{ v: 3, stages, lastStage, difficulty, volume, mute, seenShutter }`(계약서 §7). 캠페인이 들어오면 **v4**로 올린다.

```
{ v: 4,
  stages: { ... },            // v3 그대로(순수 전투 기록 — 손대지 않는다)
  campaign: {
    stages: { [id]: { cleared, firstRewardTaken, repeatCount, bestGrade } },
    heroes: { [heroId]: { level, exp, skills, tier } },
    squad:  [heroId|null × 5],
    base:   { [buildingId]: { level, built } },
    res:    { food, metal, coin },
    drone:  { level, parts },
    map:    { openedRegions: [...] },
    return: { from, stageId, squadSnapshot }   // 복귀 정보(03 §5)
  },
  daily: { date, seed, stageVersion, best }    // 일일 코스(03 §5)
}
```

**세 가지를 반드시 지킨다(03 §5).**

1. **최초 보상은 딱 한 번.** "최초 클리어 보상은 stageId + rewardVersion 기준 한 번만 지급한다. 반복 보상은 별도 표를 사용한다. **결과 화면 새로고침·재진입으로 영웅이나 재화가 중복 지급되지 않게 한다.**" → 보상 지급을 `firstRewardTaken` 플래그로 잠그고, 그 잠금을 **저장에 쓴 뒤에** 화면에 표시한다. 검사로 잠근다(같은 결과 화면을 10번 새로고침해도 자원 증가 0).
2. **복귀 정보 보존.** "기지에서 영웅 강화로 들어갔다면 완료 후 그 기지 위치로, 실패 화면에서 강화로 들어갔다면 해당 스테이지 재도전 화면으로 돌아온다. **팝업·하위 화면·앱 전환 때문에 저장된 복귀 정보가 중간 단계에서 사라지지 않게 한다.**"
3. **기존 기록 보존.** "기존 best·coins·up 데이터를 폐기하지 말고 레거시 기록으로 보존한다. **마이그레이션을 적용하기 전에 원본 저장의 백업 값을 남긴다.**" → v3 → v4 올릴 때 원본을 `starforgeRush.v3.bak`로 먼저 복사한다.

### 4-6. 원근 투영 — 규칙이 아니라 그리기다

지금 좌표는 **트랙 좌표 z 하나**로 통일돼 있고 화면 y는 렌더에서만 `y = LINE_Y - (obj.z - run.z)`로 만든다(계약서 §1). 즉 **규칙은 이미 화면과 분리돼 있다.**

그래서 원근 투영은 **이 변환 한 줄을 바꾸는 일**이지 규칙을 바꾸는 일이 아니다. 새 파일 `rush3/project.js`가 `(z, x, run.z) → { screenX, screenY, scale }`를 내놓고, 렌더만 그것을 쓴다. **충돌 판정·사거리·게이트 칸 x 범위는 트랙 좌표 그대로** 둔다.

검수1 Q3의 조건을 그대로 따른다: **"전체 규칙과 충돌 체계를 동시에 바꾸지 않는다. 가독성이 나빠지면 우선순위를 조정한다."** → 먼저 **같은 스테이지를 두 방식으로 그리는 비교 화면**을 만들어 나란히 본다. 멀리 있는 게이트 숫자가 작아져 안 읽히면(01 §11 "멀리 있는 물체도 선택에 필요한 큰 실루엣은 보여준다") **숫자만 크기를 유지하는 예외**를 두거나, 원근을 배경·도로에만 적용한다.

### 4-7. 기존 `rush/`(러너 v1)의 처리 방침 — 권고: **공존, 단 입구를 나눈다**

**사실관계.** `rush/`(14파일)는 이미 배포돼 라이브다(`https://mlight00.github.io/neon-fleet/rush.html`, STATUS). 전용 검사가 있고 계약서 §9는 **"기존 `rush/` 파일과 `tests/rush-*.test.mjs`는 한 줄도 수정하지 않는다"**를 대원칙으로 박아 두었다. rush3는 `rush/rng.js` 한 파일만 import한다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 공존(권고)** | rush.html·rush3.html을 **둘 다 남기고** 입구(index)에서 나눈다. rush3가 공개되면 rush.html은 '옛 버전' 표시 | 되돌릴 곳이 있다 · 계약서 대원칙을 그대로 지킨다 · 추가 작업 거의 없음 | 링크가 둘이라 처음 오는 사람이 헷갈릴 수 있다 → 입구에서 v3를 기본으로 |
| B. 은퇴 | rush.html을 내리고 rush3로 대체 | 입구가 하나 | rush3가 아직 초보 검증 0명인 상태에서 라이브를 대체하는 것은 이르다 |
| C. 흡수 | rush/ 코드를 rush3로 합침 | 파일 수 감소 | **계약서 대원칙 위반**이고 기존 검사가 깨진다. 얻는 것이 없다 |

**권고 = A.** 1차 공개 시점에 루트 입구에서 **"스타포지 러시(신규)"를 기본**으로 보여 주고, rush.html은 "이전 버전"으로 남긴다. 3층 검증(초보 관찰)이 끝나고 rush3가 확실히 나아진 것이 확인되면 그때 B(은퇴)를 다시 논의한다. **`rush/`의 코드와 검사는 그때까지 한 줄도 건드리지 않는다.**

- **하는 일.** 로컬 네트워크로 실제 스마트폰에서 rush3를 띄워 S1~S3를 플레이하고, 조작·가독성·성능·중단 복귀를 확인한다.
- **왜 첫 번째인가.** 한 번도 안 했고, 결과가 나쁘면 24스테이지 설계의 전제(병력 상한·글자 크기·배치 간격)가 바뀐다. **늦게 알수록 비싸다.**
- **완료 기준.** 다섯 항목이 전부 ○ 또는 기록된 △: ① 전방 게이트 숫자·통 내용물·적 범위가 읽힌다 ② 드래그가 손댄 위치로 튀지 않는다 ③ OS 제스처로 끊겨도(pointercancel) 부대가 제자리에 선다 ④ 화면 회전·앱 전환 후 복귀한다 ⑤ S3 후반(병력 100+)에서 프레임이 유지된다. **미달 항목은 통과 처리하지 않고 그대로 기록한다**(검수2 §5).

### 착수 2. 3칸 게이트 + 차폐물 격리 시제품 (묶음 B-1 순서 1)

- **하는 일.** 기존 3스테이지를 건드리지 않고 **별도 시험 구간 한 개**를 만들어 3칸 게이트와 물리 차폐물을 넣어 본다. 검수2 §4 Q5가 명시적으로 허용한 병행 작업이다.
- **왜 두 번째인가.** 결정 1·2가 어떻게 나도 이 장치는 필요하다(01 §5-3 "게이트는 1개, 2개, 3개, 앞뒤로 연달아 오는 행, 분리벽 반대편 게이트를 배치한다"). 그리고 차폐물은 **셔터 설명이 어렵다는 이사님 소감의 대안**이기도 하다.
- **완료 기준.** ① 3칸 행이 도로 80~400을 빈틈없이 덮고 부대 중심 1칸만 적용된다(01 §5-3 "여러 칸을 동시에 밟았을 때의 판정은 부대 중심 기준 1칸으로 고정") ② 차폐물이 탄을 흡수하고 통로는 막지 않는다 ③ 전용 자동검사가 붙는다 ④ 기존 243건이 그대로 통과한다(회귀 0).

### 착수 3. 통 내용물 아이콘 프롬프트 초안 (묶음 C-4 1순위)

- **하는 일.** 병사 1/2/3명 실루엣과 소총·기관총·중화기 실루엣 6장의 Gemini 프롬프트 초안을 쓴다(`newmode/이미지프롬프트_v5_v3전투장치.md`). **그림은 이사님이 만드시고 우리는 프롬프트만 드린다.**
- **왜 세 번째인가.** 결정 3(그림 순서)이 어떻게 나도 이 6장이 1순위다. 그리고 이것이 **초보 관찰(A-3) 전에 반드시 있어야 하는 그림**이다 — 01 §5-4가 "통의 숫자는 열기 위해 남은 내구다. '100'이라고 적힌 통을 열면 무조건 100명이 나오는 것으로 혼동시키지 않는다. **위에 무엇이 들어 있는지 그림으로 보여준다**"고 요구하는데, 지금은 통 그림 한 장(SUPPLY)으로 전부 그리고 있어 이 요구가 충족되지 않았다.
- **완료 기준.** 6장의 프롬프트가 기존 규약(정면 M01 첨부·투명 배경·20px 판독·아군 팔레트 cyan/ivory/gold)에 맞춰 작성되고, 이사님이 그대로 복사해 쓸 수 있는 형태다.
